# ArgonOS — возможные планы (на подумать)

> Статус: копилка идей, **не** утверждённый роадмап.
> Сюда попадает то, что выглядит полезным после обзора чужих ОС
> (Zephyr, NuttX, RIOT, Ariel, Tactility, AkiraOS, upyOS, MicroPythonOS,
> Mongoose и др.), но ещё не решено «делаем» и не вошло в
> [`04-roadmap.md`](04-roadmap.md).
>
> Правила:
> * идея не обязана сохранять модель DOS / native `.AXE` — но если ломает её,
>   это должно быть сказано явно;
> * «интересно» ≠ «в v1»; приоритет здесь — ориентир, не обязательство;
> * когда идея принята в работу — переносится в роадмап/архитектуру и из этого
>   файла либо вычёркивается, либо помечается как *принято*.

Снимок контекста Argon на момент записи: тонкое ядро над ESP-IDF, `.AXE` /
`.SYS`, арены и супервизор, VFS с дисками, пустые `class_ops`, `api->net ==
NULL`, без MMU-изоляции по замыслу.

---

## 1. Высокий интерес — усиливает текущую модель

### 1.1. Capability / permissions в манифесте `.AXE` / `.SYS`

**Откуда:** AkiraOS (Capability Guard + manifest), без их WASM.

**Суть:** приложение или драйвер заранее объявляет, что ему нужно: шины
(`I2C0`), пины, `net`, exclusive `fb0`, запись на `C:` и т.п. Ядро отказывает
в `open` / `io_claim` / сетевых вызовах, если право не заявлено.

**Почему к нам:** продолжает `ioclaim` и reslist; даёт политику доступа там,
где настоящей изоляции памяти нет и не будет. Хорошо стыкуется с будущей
подписью образа (фаза 4.5).

**Риски:** усложнение манифеста и загрузчика; ложные отказы у старых образов —
нужен переходный режим «без манифеста = как сейчас (полный trust)».

### 1.2. Заполнить `class_ops` как subsystem API

**Откуда:** модель драйверов Zephyr (device + vtable подсистемы).

**Суть:** не раздувать общий `ioctl`, а дать классовые таблицы:
`display_ops`, `block_ops`, `input_ops`, `sensor_ops`… Приложение говорит с
классом, `.SYS` регистрирует реализацию.

**Почему к нам:** поле `class_ops` уже в архитектуре и сейчас пустое; это
прямой следующий шаг модели устройств, без переноса Devicetree.

**Риски:** заморозка классовых ABI раньше согласования набора операций.

### 1.3. `chosen` в `BOARD.CFG`

**Откуда:** Zephyr `/chosen` (console, display, …).

**Суть:** среди нескольких одинаковых устройств явно выбрать системные роли:
`console=`, `display=`, `storage=`. Остальные экземпляры остаются доступны
приложениям по имени.

**Почему к нам:** `BOARD.CFG` уже «бедный DT»; не тащить YAML/DTS, а взять
одну идею выбора синглтонов.

### 1.4. Safe boot / recovery profile

**Откуда:** upyOS (recovery mode при сбое загрузки).

**Суть:** если битый `SYSTEM.CFG`, падающий `DEVICE=`, или жест (пин /
удержание клавиши / окно после сброса) — грузиться в профиль без модулей и
автозапуска, только шелл + журналирование.

**Почему к нам:** критично для плат в поле и для приёма чужих `.SYS`;
дешевле полного «промышленного» secure boot.

**Риски:** нужно аккуратно определить, что считается «безопасным минимумом»
(диски? сеть? только UART?).

### 1.5. Typed spawn params и результат приложения

**Откуда:** Tactility (Bundles вместо сырого argv; app stack + return).

**Суть:** запуск `B` из `A` с типизированным блоком параметров
(ключ → bool/int/string/blob) и возможность вернуть результат родителю.
Не обязательно полный GUI lifecycle (`on_show`/`on_hide`).

**Почему к нам:** `fm` → `edit`, будущие Settings/Wi‑Fi как отдельные `.AXE`,
ассоциации файлов. argv остаётся для шелла; bundles — для app→app.

**Риски:** новый кусок ABI (`proc`/`task`); не смешивать с DOS-командной
строкой без явных правил.

### 1.6. PATH, AUTOEXEC, ассоциации файлов

**Откуда:** NuttX (`PATH`, binfs), MicroPythonOS (intents), DOS-идиомы.

**Суть:**
* `PATH=A:\BIN;C:\BIN` — запуск `hello` без полного пути;
* `C:\AUTOEXEC.BAT` или секция в `SYSTEM.CFG` — скрипт старта после boot;
* `assoc .txt=edit.axe` (или аналог) — «открыть файл» из `fm`/шелла.

**Почему к нам:** родной DOS-UX; builtins уже дублируются как `.AXE` (`fm`) —
PATH логично продолжает это.

### 1.7. Pipes / FIFO в шелле и IPC

**Откуда:** NuttX NSH pipes; общая Unix-практика.

**Суть:** `dir | more`, именованные трубы в `T:` / VFS, простейший
межпроцессный канал сверх `spawn`/`wait` и общей ФС.

**Почему к нам:** сейчас только `>` / `>>`; фоновые процессы и утилиты без
графики выиграют сразу.

**Риски:** без нормального блокирующего pipe API легко сделать кривой UX;
после появления сети соблазн раздуть до сокетов — держать отдельно.

## 2. Средний интерес — после сети / железа / упаковки

### 2.1. Системные функции как приложения

**Откуда:** MicroPythonOS / Tactility («everything is an app»).

**Суть:** Wi‑Fi, Settings, Update, Display calibration — не куски ядра, а
`.AXE` (+ опционально фоновый service). Ядро даёт `net`/`cfg`/устройства.

**Почему к нам:** совпадает с «приложение владеет машиной»; ядро остаётся
тонким.

**Замечание:** часть сети всё равно будет в ядре (`api->net`); речь про
*пользовательский* слой конфигурации.

### 2.2. Пакет приложения: манифест + образ + подпись

**Откуда:** AkiraOS (`.akpkg`), MicroPythonOS (`.mpk`).

**Суть:** рядом с «голым» `.AXE` — контейнер: манифест (имя, версия,
capabilities, иконка?), код, подпись. Установка в `A:\APPS\` или `C:\`.

**Почему к нам:** заголовок `.AXE` уже резервирует поля под подпись; контейнер
удобнее для OTA и магазина, чем один бинарник.

**Не путать с:** сменой формата исполнения — внутри по-прежнему `.AXE`.

### 2.3. Удалённая разработка после `net`

**Откуда:** upyOS (Telnet + FTP + правка с хоста), роадмап фазы 5.

**Суть:** telnet как второй console endpoint (уже намечено в архитектуре);
FTP/HTTP к SD; опционально простой RPC (`argonctl`) для `recv`/`run`/`ps`
без сырого hex-протокола.

**Почему к нам:** `recv` по UART уже есть; сеть должна его не заменить, а
дополнить.

### 2.4. Sensor class по мотивам RIOT SAUL

**Откуда:** RIOT SAUL (единообразный API датчиков).

**Суть:** `sensor_ops`: read / configure / units / channel list — чтобы
приложение не знало, Bosch это или «сырой I2C».

**Почему к нам:** заполняет класс `SENSOR` в ABI; стыкуется с probe на I2C.

### 2.5. App → app result и стек «экранов» без LVGL

**Откуда:** Tactility (LIFO app stack).

**Суть:** даже в текстовом UI: `fm` запускает просмотрщик, по выходу
восстанавливает панели; Wi‑Fi overview запускает connect-диалог с SSID в
bundle.

**Почему к нам:** не требует LVGL; опирается на §1.5.

### 2.6. Crash UX: компактная ссылка / токен

**Откуда:** Tactility (QR с информацией о краше).

**Суть:** кроме `C:\CRASH.LOG` — однострочный summary в UART или короткий
токен/`argon://crash?...` для разбора на хосте. QR — только если есть
графика и желание.

**Почему к нам:** журнал уже есть; не хватает «скопировал строку — понял».

### 2.7. Мягкое хранение секретов (Wi‑Fi и т.п.)

**Откуда:** Tactility (шифрование creds, eFuse в ключе, предупреждение без
flash encryption).

**Суть:** не обещать безопасность при физическом доступе; но не хранить
пароли Wi‑Fi открытым текстом в `C:\` и ругаться, если secure boot / flash
encryption выключены.

**Когда:** после появления сети и места для конфигов (лучше littlefs на
`/sys`).

## 3. Низкий интерес / сознательно не сейчас

### 3.1. WASM как основной (или второй) runtime — AkiraOS

Изоляция и переносимость привлекательны, но это другая ОС: другой тулчейн,
другая модель памяти, цена скорости. Имеет смысл только как *опциональный*
`.WAM`/AOT рядом с `.AXE` в далёком будущем, не как замена ABI.

### 3.2. Полный POSIX / погоня за NuttX

Куски (pipes, PATH, spawn) — да. Эмуляция Linux userspace на S3 — нет;
размывает DOS-контракт и бюджеты.

### 3.3. MicroPython / upyOS / PY-DOS как ядро или обязательный слой

Полезно как *гостевое* приложение когда-нибудь (`PYTHON.AXE`?), вредно как
замена C ABI.

### 3.4. LVGL в ядре (Tactility / MicroPythonOS)

Допустимо как библиотека или `.AXE`/`.SYS` для touch-плат. В ядро — только
если появится отдельный продукт «Argon Tablet»; сейчас текстовый экран +
`gfx` ближе к замыслу.

### 3.5. Ariel OS (Rust), FhatOS, B3OS

Ariel: memory safety через язык не переносится без смены стека; из идей —
разве что deny-by-default capabilities (§1.1). FhatOS / B3OS — мало зрелости
и пересечения.

### 3.6. Облачная IoT-обвязка Mongoose (AWS и т.п.)

Не цель Argon. Полезный кусок — тонкий встроенный HTTP/RPC (§2.3), без
привязки к облаку вендора.

### 3.7. Магазин приложений «как Android»

Только после `net` + подписи + пакета (§2.2). До этого — каталог на SD и
ручная установка.

## 4. Уже сделано у нас, у других называется иначе

Не план, а напоминание, чтобы не «изобретать повторно»:

| У других | У Argon |
|---|---|
| NuttX NXFLAT (I-space / D-space, XIP) | split `.AXE` + arena / PSRAM data / flash XIP |
| Flipper / Tactility app platform на MCU | процессы + ABI + загрузка с SD |
| Zephyr board descriptions | `BOARD.CFG` + board packs (частично) |
| Headless build | UART / QEMU-first, дисплей опционален |

---

## 5. Черновой shortlist (если выбирать пять)

Ориентир «что разобрать первым», не коммит в роадмап:

1. Capability/permissions в манифесте (§1.1)
2. `class_ops` + `chosen` (§1.2, §1.3)
3. Safe boot / recovery (§1.4)
4. PATH + AUTOEXEC + assoc (§1.6)
5. Typed spawn params / app-result (§1.5)

Pipes (§1.7) и пакет+подпись (§2.2) логично стыковать с уже запланированными
фазами IPC/сети/4.5, а не плодить параллельный трек.
