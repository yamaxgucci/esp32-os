Цель v1 [Т-37]: *плата загружается, работают встроенные команды, с карты
запускается приложение с графикой, работает внешняя USB-клавиатура.*

## Спайк S-1 — исполнение кода из PSRAM  ⚠ ограничивает размер кода

Проверить на S3: `esp_mmu_map(MMU_TARGET_PSRAM, MMU_MEM_CAP_EXEC)`, запись кода
через data-алиас, сброс кэшей, вызов. Замерить скорость относительно SRAM и
flash-XIP. Результат определяет §3.2 архитектуры.

*Требует железа*, и QEMU здесь не заменитель: он не моделирует кэш, поэтому
«работает в эмуляторе» ничего не говорит про писать-через-одну-шину-исполнять-
через-другую. Фазу 2 больше не блокирует — приложения запускаются, код лежит в
арене D/IRAM, данные в PSRAM. Упирается в этот спайк только размер **кода**.

## Спайк S-2 — релокации Xtensa

Собрать тестовое приложение `ld -r`, разобрать таблицы релокаций, реализовать
и покрыть host-тестами применение `R_XTENSA_32`, `R_XTENSA_SLOT0_OP`,
`R_XTENSA_PLT`, литеральные пулы. Без железа проверяется на дампах.

## Фаза 1 — «плата загружается и отвечает»

1. ✅ Загрузка ядра, определение чипа, профиль (`full`/`lite`/`nano`)
2. ✅ Слой описания платы: дефолты чипа + `C:\BOARD.CFG`
   (см. `docs/03-board-config.md`); ⬜ вкомпилированные board pack'и под
   конкретные платы и их автовыбор
3. ✅ Журнал логов: кольцевой буфер 4 КБ в internal SRAM, escape-последователь­
   ности вырезаются на входе, счётчик потерянных строк точный (производный, а не
   инкрементальный). Всё логируемое — ядром, ESP-IDF, драйверами — попадает
   сначала в журнал, экран стал одним из его читателей. Команда `log`.
   ⬜ Сохранение журнала в файл при крэше (нужен супервизор)
4. ✅ Консоль: текстовый экран, VT100-рендер, разбор ввода, UART-endpoint,
   мультиплексор с очередью событий
5. VFS: ✅ ядро слоя (монтирование, дескрипторы, владельцы, eject),
   ✅ ramfs `/tmp` (`T:`), ✅ FAT на внутреннем flash `/sys` (`C:`),
   ✅ FAT на SD `/sd` (`A:`) — SDMMC и SPI, через адаптер к VFS от ESP-IDF;
   ⬜ littlefs вместо FAT для `/sys` — переживает пропадание питания посреди
   записи, что важно для журнала и конфигов; это замена одного вызова в
   `storage.c`
6. ✅ `BOARD.CFG` и `SYSTEM.CFG` читаются на стадии `config`
7. ✅ Шелл: редактор строки с историей, разбор команд, перенаправление вывода,
   смена диска по `a:`, `dir cd type copy del md rd ren mount format hexdump
   ver mem boot uptime cls echo color ps errorlevel reboot help`
8. ⬜ Кодовая страница экрана (CP437/CP866, аналог `chcp`) — сейчас ячейка
   хранит один байт и не-ASCII показывается как `?`

**Готово, когда:** плата стартует за <400 мс, по UART доступен `A:\>`,
работают файловые команды на реальной SD.

**Уже работает в QEMU:** загрузка, приглашение, редактирование строки, все
встроенные команды, три диска (`A:` SD, `C:` внутренний flash, `T:` RAM),
копирование между дисками, `format a:`, перенаправление `dir > files.txt`,
чтение `BOARD.CFG`. Проверяется `argon test`, экран из транскрипта
восстанавливается `build-host\vtdump.exe`. Карта: `argon test -Sd`.

## Фаза 2 — «запускается приложение»

1. ⬜ Менеджер памяти: арены процессов, `AG_MEM_*` capabilities
2. ✅ Загрузчик: формат `.AXE`, инструмент `tools/mkaxe.py`, релокация
   абсолютных слов, проверка заголовка. **Спайк S-2 закрыт без железа:**
   декодирование инструкций Xtensa не нужно — см. §3.1 архитектуры
3. ⬜ Модель процессов, ресурсный список, exec/spawn/wait/kill.
   Своя задача и свой стек у приложения уже есть ✅, но это ещё не процесс:
   нет ресурсного списка, и дикий указатель по-прежнему достаёт остальную систему
4. ⬜ Супервизор: watchdog, `Ctrl-C`, `Ctrl-Alt-Del`, перехват исключений,
   crash-record
5. Таблицы ABI: ✅ `sys mem fs con time`; ⬜ `task proc cfg io dev inp gfx`
6. ⬜ SDK: `libargon` как библиотека, шаблон приложения; сборка `.AXE` ✅,
   пример `apps/hello` ✅
7. ⬜ Команды `ps kill fg`; ✅ `run`, ✅ `recv` (приём файла как hex через
   консоль — как доставлять приложение на плату без картридера)
8. ✅ **Разделение образа на две части** — код в арену D/IRAM, данные и bss в
   окно данных PSRAM, у релокации признак части. Лимит на данные снят: проверено
   приложением с 512 КБ bss при арене 64 КБ. Осталось поднять лимит на **код** —
   это спайк S-1, ему нужна плата

**Готово, когда:** `run hello.axe` с карты работает, `Ctrl-Alt-Del` снимает
зависшее приложение, память после снятия возвращается полностью.

**Уже работает в QEMU:** приложение собирается `mkaxe.py`, передаётся `recv`,
загружается двумя частями и исполняется на своей задаче, печатает на консоль
через таблицу ABI, возвращает код завершения; образ, который не влезает в арену,
получает отказ с объяснением. Правильность релокации доказана тестом: образ,
перенесённый загрузчиком, байт-в-байт совпадает с прямой линковкой по тем же
адресам — причём части в фикстурах разнесены на *разные* расстояния, так что один
общий сдвиг такой тест не проходит.

## Фаза 2.5 — документация для разработчиков

Отдельная фаза, а не «допишем потом»: ABI объявлен контрактом со сторонними
разработчиками [Т-13], а контракт без описания контрактом не является.

Делать **после** модели процессов: подтаблицы `task` и `proc` появятся там же,
и описывать ABI до них — значит переписывать дважды.

1. `docs/sdk/01-getting-started.md` — от нуля до работающего приложения:
   установка тулчейна, сборка `.AXE`, доставка на плату, запуск
2. `docs/sdk/02-api-reference.md` — полный разбор `argon/abi.h` по подсистемам:
   что делает каждый вызов, что возвращает, чего **не** делает; правила
   совместимости и `AG_HAS()`
3. `docs/sdk/03-application-anatomy.md` — `AG_APP()`, `ag_main`, аргументы, код
   возврата, чего нет (libc по умолчанию, потоки до подтаблицы `task`)
4. `docs/sdk/04-axe-format.md` — формат образа для тех, кто пишет свои
   инструменты сборки
5. `docs/sdk/05-drivers.md` — после модели устройств
6. `docs/user/01-shell.md` — все команды с примерами, перенаправление, диски
7. `docs/user/02-board-setup.md` — «как поднять ArgonOS на незнакомой плате»,
   расширение `03-board-config.md`
8. `apps/` — примеры, которые собираются и работают: hello, чтение файла,
   работа с диском, позже графика
9. README на английском как точка входа для внешнего читателя

**Готово, когда:** сторонний разработчик собирает и запускает своё приложение,
не читая исходники ядра.
