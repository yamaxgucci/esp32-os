# Формат образа `.AXE`

Для тех, кто пишет свои инструменты сборки: компилятор, линковщик, упаковщик
ресурсов. Всё, что нужно знать, чтобы получить файл, который система запустит, — и
чтобы понимать отказы, если не запустит.

Определение формата — [`argon/axe.h`](../../sdk/include/argon/axe.h). Рабочая
реализация — [`tools/mkaxe.py`](../../tools/mkaxe.py), 500 строк питона, включая
разбор ELF. Загрузчик — [`axeload.c`](../../components/argon_kernel/src/loader/axeload.c),
и он проще: копирование, проход по списку смещений и переход.

## Идея

Приложение линкуется на хосте по номинальным адресам, а грузится на устройстве
туда, где есть место. Обычно из этого следует полноценная релокация с разбором
инструкций. Здесь — нет, и вот почему.

Каждая часть образа линкуется **одним непрерывным блоком**. Перенос блока
переносит вместе и PC-относительную инструкцию, и её цель, так что расстояние
между ними не меняется. Править остаётся только **абсолютные 32-битные слова**:
записи литерального пула и инициализированные указатели.

Измерено, а не предположено: тот же объектный файл, слинкованный по адресам,
отличающимся на `0x10000`, дал образы, различающиеся ровно в шести байтах — по
одному в каждом из шести литеральных слов, которые держат адрес. Все инструкции
совпали.

Поэтому в ядре нет ни разборщика ELF, ни декодера инструкций. Сложное делает
инструмент сборки на машине, где сложность дешёвая.

## Две части

| Часть | Что в ней | Куда грузится |
|---|---|---|
| код | литералы, `.text`, `.hot_rodata`, заголовок приложения | арена в D/IRAM, исполняемая |
| данные | `.rodata`, `.data`, `.bss` | окно данных PSRAM, записываемая |

Части две потому, что памяти, которая одновременно исполняемая и записываемая
через один адрес, на этом семействе почти нет. Подробно — §3.2
[архитектуры](../00-architecture.md).

Части переезжают **независимо и на разные расстояния**. Значит, слово с адресом
обязано сказать, в какую часть этот адрес смотрит, — и в какой части лежит само.
Оба признака влезли в младшие два бита смещения: смещения выровнены на слово,
эти биты всегда нули.

```c
#define AG_AXE_R_OFFSET(e) ((e) & ~3u)
#define AG_AXE_R_IN_DATA 0x1u   /* само слово лежит в части данных */
#define AG_AXE_R_TO_DATA 0x2u   /* адрес в нём смотрит в часть данных */
```

Все четыре комбинации встречаются в обычном приложении:

| Слово | Адрес в нём | Пример |
|---|---|---|
| в коде | в код | литерал с адресом функции |
| в коде | в данные | литерал с адресом переменной или константы |
| в данных | в данные | таблица указателей на строки |
| в данных | в код | таблица указателей на функции — и таблица переходов от `switch`, которую строит компилятор |

## Файл

```
+---------------------+ 0
| ag_axe_header_t     | 176 байт
+---------------------+ code.offset
| часть кода          | code.file_size байт
+---------------------+ data.offset
| часть данных        | data.file_size байт (bss в файле не лежит)
+---------------------+ reloc_offset
| таблица релокаций   | reloc_count слов по uint32
+---------------------+
```

Всё little-endian. Заголовок:

| Смещение | Размер | Поле | Значение |
|---|---|---|---|
| 0 | 4 | `magic` | `"AXE1"` |
| 4 | 2 | `abi_major` | против какой версии ABI собрано |
| 6 | 2 | `abi_minor` | |
| 8 | 2 | `arch` | 1 = xtensa, 2 = riscv32 |
| 10 | 2 | `header_size` | ≥ 176; больше — заголовок новее |
| 12 | 4 | `flags` | `ag_axe_flags` |
| 16 | 16 | `code` | `base`, `size`, `file_size`, `offset` |
| 32 | 16 | `data` | то же для части данных |
| 48 | 4 | `entry` | адрес `ag_main` **как слинковано** |
| 52 | 4 | `api_slot` | адрес слота `g_ag_api`, как слинковано |
| 56 | 4 | `reloc_offset` | смещение таблицы релокаций в файле |
| 60 | 4 | `reloc_count` | сколько в ней слов |
| 64 | 4 | `stack_size` | 0 — по умолчанию |
| 68 | 4 | `heap_size` | 0 — по умолчанию |
| 72 | 32 | `name` | с завершающим нулём |
| 104 | 16 | `version` | |
| 120 | 32 | `author` | |
| 152 | 24 | `reserved[6]` | нули; задел под подпись и ресурсы |

Каждая часть описана четвёркой: адрес линковки, сколько памяти нужно (`size`,
вместе с bss), сколько из этого лежит в файле (`file_size`) и где в файле
(`offset`). Разница `size - file_size` — bss, её обнуляет загрузчик. Для части
кода она всегда ноль, для части данных обычно нет. Часть с `size == 0`
отсутствует — это нормально для приложения без записываемых статиков.

Ни точку входа, ни слот таблицы вызовов **не надо искать по имени**: их адреса в
заголовке, поэтому символьной таблицы в файле нет вообще.

## Что делает загрузчик

```c
code_bias = где_лежит_код - header.code.base;
data_bias = где_лежат_данные - header.data.base;

for (каждое слово в таблице) {
    часть  = (entry & AG_AXE_R_IN_DATA) ? данные : код;
    слово  = читать32(часть + AG_AXE_R_OFFSET(entry));
    слово += (entry & AG_AXE_R_TO_DATA) ? data_bias : code_bias;
    писать32(часть + AG_AXE_R_OFFSET(entry), слово);
}
```

И всё: обнулить bss, добавить смещение к списку слов, записать адрес таблицы
вызовов в `api_slot`, перейти на `entry`. Ни одной инструкции загрузчик не
разбирает.

## Что загрузчик отказывается принимать

Каждая проверка — из `ag_axe_validate`, и каждая означает, что файл противоречит
сам себе. Свой инструмент сборки полезно проверять по этому списку.

| Условие | Код |
|---|---|
| файл короче заголовка, не тот `magic`, `header_size` меньше 176 | `EFORMAT` |
| `arch` не совпал с процессором | `ENOTSUP` |
| `abi_major` не совпал или `abi_minor` образа новее системного | `EABI` |
| `name`, `version` или `author` без завершающего нуля | `EFORMAT` |
| `code.size == 0` — приложения без кода не бывает | `EFORMAT` |
| `code.file_size != code.size` — часть кода исполняется как приехала, bss в ней быть не может | `EFORMAT` |
| `file_size > size` у любой части | `EFORMAT` |
| `base` или `size` не кратны 4 | `EFORMAT` |
| часть выходит за пределы 32-битного адресного пространства | `EFORMAT` |
| `offset + file_size` больше размера файла | `EFORMAT` |
| части перекрываются — адрес стал бы неоднозначным | `EFORMAT` |
| `AG_AXE_CONTIGUOUS` есть, а данные не сразу за кодом | `EFORMAT` |
| `AG_AXE_CONTIGUOUS` есть, а части данных нет | `EFORMAT` |
| `reloc_count` больше 65536, или таблица не влезает в файл | `EFORMAT` |
| `entry` вне части кода | `EFORMAT` |
| `api_slot` ни в одной из частей | `EFORMAT` |
| смещение релокации выходит за пределы **хранимых** байт своей части | `EFORMAT` |
| релокация ссылается на часть данных, которой в образе нет | `EFORMAT` |
| часть больше 8 МБ | `EFORMAT` |

Отдельно про `entry`: он обязан быть в части кода, а `api_slot` может быть в
любой, и на практике он в bss части данных.

## Слитный образ и RISC-V

У RISC-V с моделью `medany` код достаёт свои данные PC-относительно. Расстояние
между частями становится частью контракта, и менять его нельзя. Такой образ
собирается **слитным**: обе части в одном блоке, флаг `AG_AXE_CONTIGUOUS`
требует от загрузчика положить данные ровно за кодом и относить обе части одним
смещением.

Формат при этом тот же самый — меняется только обещание о размещении. Выравнивание
между частями (`ALIGN(16)`) складывается в `code.size`, потому что загрузчику
обещано, что данные начинаются там, где кончается код.

Xtensa так собирать тоже можно (`--contiguous`), и это проверяется тестами, но
смысла на нём нет: слитный образ целиком должен влезть в арену кода, то есть
теряется всё, ради чего части разделены.

## Как это проверяется

Правильность релокации нельзя проверить «запустилось — значит верно»: неверно
перенесённое слово может годами не попадаться. Поэтому проверка другая.

**Образ, перенесённый загрузчиком, обязан байт в байт совпасть с образом, прямо
слинкованным по тем же адресам.** Фикстуры в
[`host-tests/fixtures`](../../host-tests/fixtures) — это один и тот же исходник,
слинкованный по двум парам адресов; тест грузит первый по адресам второго и
сравнивает. Части в фикстурах разнесены на **разные** расстояния, так что
загрузчик, использующий одно смещение на обе, такой тест не проходит.

Фикстура специально содержит все четыре комбинации признаков, включая таблицу
переходов, которую ставит компилятор, а не автор теста. Пересобрать её:
`host-tests/fixtures/regenerate.ps1`; запустить тесты: `argon tests`.

Свой инструмент сборки полезно проверять так же: собрать одно и то же по двум
парам адресов и сравнить результат переноса с прямой линковкой. Это ловит все
ошибки классификации сразу.

## Чего в формате нет

* **символьной таблицы и отладочной информации.** Отладка — по `--keep-elf`:
  промежуточный ELF содержит всё, и смещения в нём те же, что в образе;
* **секций сверх двух частей.** Ресурсы (иконки, строки, ассеты) появятся в полях
  `reserved`;
* **подписи.** Место оставлено, проверки нет;
* **сжатия.** Образ копируется в память как есть;
* **зависимостей от других образов.** Приложение ссылается только на себя и на
  таблицу вызовов; ссылка на что-либо ещё — отказ сборки.
