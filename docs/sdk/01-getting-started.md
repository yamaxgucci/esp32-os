# От нуля до работающего приложения

Что нужно поставить, как собрать `.AXE`, как доставить его в систему и как
запустить. Ядро читать не требуется — весь контракт описан в
[02-api-reference.md](02-api-reference.md), а этот документ доводит до первого
запуска.

Приложение ArgonOS — это **нативный код**, а не скрипт и не байт-код. Собирается
тем же GCC, что и прошивка, только линкуется в свой формат образа (`.AXE`) и
обращается к системе через таблицу вызовов, а не через libc.

## 1. Что должно быть на машине

| Что | Зачем | Проверка |
|---|---|---|
| **ESP-IDF 5.5** или новее | из него берётся компилятор `xtensa-esp32s3-elf-gcc` | `idf.py --version` |
| **Python 3.9+** | `tools/mkaxe.py` — сборщик образа | `python --version` |
| Исходники ArgonOS | SDK-заголовки и сам сборщик | `sdk/include/argon/abi.h` на месте |

Плата **не нужна**: система загружается в QEMU из состава ESP-IDF, и приложение
там запускается ровно так же, как на железе. Всё, что описано ниже, проверено
именно так.

Пути к ESP-IDF на конкретной машине не коммитятся. Либо переменные окружения
(`ARGON_IDF_PATH`, `ARGON_IDF_TOOLS_PATH`, `ARGON_PYTHON`), либо файл
`tools\local-env.ps1`:

```powershell
$env:ARGON_IDF_PATH       = 'D:\Espressif\esp-idf'
$env:ARGON_IDF_TOOLS_PATH = 'D:\Espressif\tools'
$env:ARGON_PYTHON         = 'D:\dev\python312\python.exe'
```

Компилятор появляется в `PATH` после загрузки окружения — точка в начале
обязательна, скрипт должен выполниться в текущем процессе:

```powershell
. .\tools\idf-env.ps1
```

## 2. Приложение целиком

```c
#include <argon/argon.h>

AG_APP("HELLO", "1.0", "you", 0);

int ag_main(int argc, char **argv)
{
    ag_printf("Hello from ArgonOS, %d argument(s)\n", argc);
    for (int i = 0; i < argc; i++) {
        ag_printf("  argv[%d] = %s\n", i, argv[i]);
    }
    return 0;
}
```

Три обязательные вещи и ничего больше:

* `#include <argon/argon.h>` — inline-обёртки над таблицей вызовов; каждая
  разворачивается в один косвенный вызов без лишнего кадра;
* `AG_APP(...)` — заголовок образа: имя, версия, автор, флаги. Один раз на
  приложение, в файле с `ag_main`;
* `int ag_main(int argc, char **argv)` — точка входа. Не `main`: `main` в системе
  без libc никто не вызовет, а имя точки входа записано в заголовок образа.

Готовый шаблон лежит в [`sdk/templates/hello/hello.c`](../../sdk/templates/hello/hello.c).
Подробнее об устройстве приложения — [03-application-anatomy.md](03-application-anatomy.md).

## 3. Сборка образа

```bash
python tools/mkaxe.py --arch xtensa --gcc xtensa-esp32s3-elf-gcc --include sdk/include -o HELLO.AXE hello.c
```

Печатает то, что получилось, — это первое, на что стоит смотреть:

```
HELLO.AXE: xtensa, code 524 bytes, data 524576 bytes (284 stored, 524292 bss), 284 bytes of constants in the data part, 14 relocations
```

* **code** — часть, которая попадёт в исполняемую арену. Она маленькая и
  дорогая: по умолчанию 64 КБ на все процессы;
* **data** — константы, `.data` и `.bss`; едет в PSRAM, ограничена только
  свободной памятью, мегабайты;
* **stored** — сколько из этого лежит в файле; `bss` в файле не лежит, его
  обнуляет загрузчик;
* **relocations** — сколько абсолютных слов правит загрузчик при запуске.

Опции `mkaxe.py`, которые могут понадобиться:

| Опция | Что делает |
|---|---|
| `--arch xtensa\|riscv32` | целевая архитектура; `riscv32` всегда собирается слитным образом |
| `--gcc <путь>` | компилятор; для RISC-V — `riscv32-esp-elf-gcc` |
| `--include <каталог>` | добавляется в путь поиска заголовков; `sdk/include` нужен всегда |
| `--cflags "..."` | заменяет флаги компиляции целиком (по умолчанию `-Os -ffunction-sections -fdata-sections`) |
| `--rodata data\|code` | где размещать константы: в части данных (по умолчанию) или в части кода |
| `--libs <имя>` | ещё один архив на линковке, без `-l` (`libgcc` линкуется всегда). Из архива берутся только те объекты, которые закрывают ещё не разрешённый символ, поэтому `--libs c` ради `setjmp` не тащит malloc из newlib поверх вашего. Так собирается `MD.AXE`: у Musashi address error разматывается через `setjmp` |
| `--keep-elf <файл>` | сохранить промежуточный ELF — по нему удобно смотреть карту и дизассемблировать |
| `--code-base` `--data-base` | адреса линковки; менять нужно только при отладке релокации |

Файлов на входе может быть несколько, включая уже собранные `.o`:

```bash
python tools/mkaxe.py --arch xtensa --gcc xtensa-esp32s3-elf-gcc \
    --include sdk/include --include apps/fm -o FM.AXE apps/fm/fm.c apps/fm/fmops.c
```

Чего в сборке нет: libc, стартового кода, конструкторов C++, оптимизации при
линковке между файлами. `-nostdlib` — осознанное решение, см.
[03-application-anatomy.md](03-application-anatomy.md#нет-libc).

## 4. Доставка в систему

Три способа, по убыванию удобства.

### Карта памяти

Скопировать `.AXE` на карту с ПК, вставить в плату — файл виден как `A:\HELLO.AXE`.
Самый быстрый путь, если есть картридер.

### `recv` — приём по консоли

Плата без картридера всё равно должна как-то получать приложения. Команда `recv`
читает hex-строки прямо из консоли и пишет файл:

```
C:\> recv t:\hello.axe
send hex, END to finish
41584531 0000 0200 ...
END
1040 bytes written
```

Протокола нет намеренно: ничего не нужно ни на плате, ни на другом конце, и это
переживает терминал, съедающий управляющие символы. Отправитель — любой скрипт,
печатающий hex в порт; обвязка QEMU (`tools/qemu-boot.ps1`) делает именно это и
дополнительно **сверяет число записанных байт с размером файла** — байты в
последовательной линии теряются молча, и файл приезжает тихо неверным.

### QEMU

Всё сразу, одной командой: собрать образ flash, загрузиться, положить файл,
выполнить команды и напечатать получившийся экран.

```powershell
.\argon.cmd test -Put 'build\HELLO.AXE=t:\hello.axe' 'run t:\hello.axe one two'
```

## 5. Запуск

```
C:\> run t:\hello.axe one two
```

Что при этом происходит, видно в журнале (`log`):

```
I (1464) loader: HELLO: xtensa v1.0, code 524 B at 0x40387100, data 524576 B at 0x3c06bb90, 14 relocations
hello from ArgonOS, 3 argument(s)
  argv[0] = t:\hello.axe
  argv[1] = one
  argv[2] = two
```

`argv[0]` — путь, которым приложение запустили; по нему программа может найти
свои файлы. Код возврата `ag_main` остаётся в `errorlevel`:

```
C:\> errorlevel
0
```

Ключи и особые случаи:

| Команда | Что делает |
|---|---|
| `run <файл> [аргументы]` | запуск на переднем плане, шелл ждёт |
| `run /b <файл>` | запуск в фоне, печатает `started pid N` |
| `ps` | что загружено и в каком состоянии |
| `kill <pid>` | снять процесс |
| `fg <pid>` | вернуть фоновый процесс на передний план и дождаться |
| `Ctrl+C` | попросить приложение остановиться (см. `ag_interrupted`) |
| `Ctrl+\` | снять приложение, которое не слушает `Ctrl+C` |

## 6. Когда не запускается

Загрузчик отказывается словами, а не падением. Все сообщения — из одного места
(`print_load_error` в шелле), и каждое означает конкретную причину:

| Сообщение | Что случилось |
|---|---|
| `file not found` | нет такого файла; проверьте диск и путь |
| `not an ArgonOS application` | не тот формат: нет `AXE1` в начале или заголовок противоречит сам себе |
| `built for a different processor` | образ собран для другой архитектуры (`--arch`) |
| `built for a different version of this system` | ABI major не совпал, или minor образа новее, чем у системы |
| `not enough memory to load it` | часть кода не влезла в арену либо не нашлось памяти под данные; журнал печатает точные числа |
| `too many applications are loaded` | больше четырёх процессов одновременно (`AG_PROC_MAX`) |
| `too many arguments` | аргументы вместе не влезли в 256 байт. Слов больше 16 не отказ, а молчаливое отбрасывание лишних — предел один и тот же и в шелле, и в `proc->spawn` |

Отдельный случай — приложение собралось, но `mkaxe.py` отказался:

* `no g_ag_api; is AG_APP() missing?` — забыт `AG_APP(...)`;
* `the application defines no ag_main` — точка входа названа иначе;
* `refers to symbol '...', which is not in the image` — вызов функции, которой
  в образе нет: скорее всего что-то из libc, которой у приложения нет;
* `no code in the image` — все входные файлы оказались пустыми для линковщика.
