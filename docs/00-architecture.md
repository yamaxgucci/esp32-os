# ArgonOS — архитектура

> Статус: v0.1, черновик для утверждения.
> Документ фиксирует решения, принятые по итогам первичного опроса требований.
> Каждое решение помечено источником: **[Т-N]** — ответ на вопрос N анкеты.

---

## 0. Что это такое

**ArgonOS** — операционная система для микроконтроллеров ESP32 с моделью
исполнения в стиле MS-DOS: *приложение владеет машиной*, ОС — тонкий слой
сервисов, а не менеджер ресурсов, который постоянно вмешивается.

Отличия от DOS, продиктованные требованием промышленной применимости:

| | MS-DOS | ArgonOS |
|---|---|---|
| Планировщик | нет | вытесняющий RTOS-планировщик, но приложение получает выделенное ядро CPU |
| Сеть/USB | внешние TSR | штатные подсистемы ядра, работают параллельно приложению |
| Зависшее приложение | reset | супервизор снимает задачу и освобождает **все** её ресурсы |
| Драйверы | `DEVICE=` в CONFIG.SYS | статические + загружаемые модули `.SYS` с единой моделью устройств |
| Совместимость ПО | абсолютная | версионированный ABI (append-only) |

Имя: **ArgonOS** (аргон — инертный газ: слой между приложением и железом,
который ни во что не вмешивается). Префикс всех публичных API — `ag_`.

Соглашения, унаследованные от DOS намеренно:
* исполняемые файлы приложений — `*.AXE` (**A**rgon e**X**ecutabl**E**);
* драйверы — `*.SYS`;
* конфигурация системы — `SYSTEM.CFG`, конфигурация платы — `BOARD.CFG`;
* встроенный шелл с приглашением `A:\>` и командами `dir`, `copy`, `type`, `cls`, …

## 1. Целевое железо [Т-1..Т-5]

**Основная платформа: ESP32-S3.** Причина — это единственный широко доступный
чип семейства, у которого одновременно есть: PSRAM с возможностью **исполнения
кода** через MMU/кэш, USB-OTG (host для клавиатуры), Wi-Fi/BLE и два ядра.

Архитектура пишется так, чтобы порт на **ESP32-P4** (RISC-V, 400 МГц, PMP,
больше памяти) был работой в слое HAL, а не переписыванием ядра. Классический
ESP32 и C3/C6 поддерживаются в урезанном профиле (см. §11).

**Одни исходники на семейство ESP32.** Ядро, приложения и Argon CC — одно
дерево. Другой чип семейства — пересборка (`idf.py set-target`,
`mkaxe.py --arch xtensa|riscv32`), не второй репозиторий и не один бинарник:
`.AXE` нативный, Xtensa-образ на C6/P4 не едет. Ветки в коде — по возможности
(профиль, executable PSRAM, число ядер, USB host), не по имени `esp32s3`.
`BOARD.CFG` ниже выбирает плату **одного** SoC. Чипы вне Espressif в эту
схему не входят.

**Требования к плате (минимальный профиль `full`):**

| Ресурс | Минимум | Комфорт |
|---|---|---|
| Чип | ESP32-S3 | ESP32-S3 / P4 |
| PSRAM | 4 МБ (quad) | 8–16 МБ (octal) |
| Flash | 8 МБ | 16 МБ |
| SD | SPI | SDMMC 4-bit |

Профиль `lite` (без PSRAM, приложение целиком в internal SRAM: код в арене,
данные из внутренней кучи) — для ESP32/C3/C6. Определяется автоматически на
старте.

**Носители [Т-3]:** поддерживаются оба режима SD — `SDMMC` (1/4-bit) и `SPI`,
выбор в `BOARD.CFG`. Дополнительно: внутренний flash (littlefs), USB Mass Storage
(и как host, и как device — плата видна с ПК как диск).

**Мультиплатформенность [Т-4, Т-5].** Единственный образ прошивки должен
подниматься на разных платах. Реализуется через **board pack** — описание платы:

1. Компилируемые board pack'и для популярных плат (ESP32-S3-DevKitC,
   ESP32-S3-BOX-3, LilyGO T-Display-S3, «Cheap Yellow Display» и т. д.).
2. Файл `BOARD.CFG` в корне SD или во внутреннем flash — переопределяет всё
   (пины, шины, контроллер дисплея, режим SD). Позволяет поднять ОС на
   незнакомой плате **без перекомпиляции**.
3. Выбор пакета: запись в NVS → efuse-метка → `BOARD.CFG` → автодетект → generic.

## 2. Фундамент: ESP-IDF, но своя надстройка [Т-6, Т-7]

Требование «сеть и USB работают без проблем» закрывает вопрос о bare-metal:
Wi-Fi — бинарный блоб, жёстко завязанный на FreeRTOS; USB-стек, lwIP, OTA — это
человеко-годы работы. **ESP-IDF используется как HAL и набор нижних драйверов.**

Но ArgonOS — не «приложение под ESP-IDF». Своими являются:

* модель процессов и загрузчик приложений;
* менеджер памяти с учётом владельца (per-process arena);
* VFS-надстройка, модель устройств и драйверов;
* консольная подсистема (мультиплексор текстовых терминалов);
* супервизор, watchdog приложений, восстановление;
* шелл и системные утилиты;
* публичный ABI для сторонних приложений.

Из ESP-IDF берутся: загрузчик 2-й ступени, FreeRTOS, драйверы шин, Wi-Fi/BLE,
lwIP, TinyUSB, esp_mmu, esp_psram, spi_flash, OTA.

> **Стоимость решения:** мы наследуем ~40–60 КБ SRAM накладных расходов IDF+FreeRTOS
> ещё до старта ArgonOS, и ~50 КБ сверху при включённом Wi-Fi. См. §10.

### Модель ядер CPU («DOS на core 1»)

```
core 0 (PRO)                          core 1 (APP)
├── ESP-IDF: Wi-Fi, lwIP, USB, timers  └── задача переднего приложения
├── ArgonOS: supervisor (prio 20)          (prio 5, единственная задача
├── ArgonOS: console, devmgr                на ядре по умолчанию)
└── фоновые приложения (если есть)
```

Приложение получает **всё ядро 1** и не конкурирует ни с чем, кроме собственных
потоков. Это и есть «DOS-ощущение»: детерминированная скорость, никаких
неожиданных провалов производительности из-за системных задач.

Параметр `kernel.app_core_exclusive=1` (по умолчанию) запрещает планировщику
ставить на core 1 что-либо кроме приложения.

## 3. Формат и загрузка приложений [Т-9, Т-12, Т-16]

Приоритет — **скорость исполнения**, время загрузки не важно, изоляция не нужна.
Это однозначно выбирает **нативный машинный код**, без VM и без WASM.

### 3.1 Формат: `.AXE` — цельный образ и таблица абсолютных слов

**Решение изменено по итогам измерения.** Изначально планировался ET_REL с
применением релокаций Xtensa на устройстве. Это потребовало бы декодирования
инструкций (`R_XTENSA_SLOT0_OP` правит операнд в слоте инструкции, и надо знать,
какой именно) — сотни строк тонкого кода в ядре.

Наблюдение, которое это убирает: **если образ слинкован как один непрерывный
блок, то при переносе по другому адресу все PC-относительные инструкции
остаются верными** — сдвигаются и инструкция, и её цель. Править надо только
абсолютные 32-битные слова, то есть записи литерального пула, содержащие адреса.

Проверено, а не предположено: один и тот же объект слинкован по двум базам с
разницей `0x10000`; образы отличались **ровно в шести байтах** — по одному в
каждом из шести литеральных слов, содержащих адрес. Ни одна инструкция не
изменилась. `readelf -r` подтверждает: релокаций всего два вида,
`R_XTENSA_32` (6 штук) и `R_XTENSA_SLOT0_OP` (9 штук, все PC-относительные).

Отсюда формат `.AXE` (`sdk/include/argon/axe.h`): заголовок, образ, таблица
смещений слов. Загрузчик делает копию, проход по списку смещений с добавлением
смещения загрузки, и переход. **Ни ELF-парсера, ни декодера инструкций в ядре
нет.** Сложность живёт в `tools/mkaxe.py`, на машине, где она дешёвая.

Побочная выгода: то же самое работает для RISC-V без изменений в ядре — там
абсолютные слова это `R_RISCV_32`, а таблицу строит тот же инструмент.

Отвергнутые варианты и почему:

| Вариант | Почему нет |
|---|---|
| ET_REL + релокации на устройстве | требует декодирования инструкций Xtensa; измерение показало, что не нужно |
| WASM (WAMR) | 1.5–3× потеря скорости; изоляция нам не нужна [Т-12] |
| `-fPIC` shared object | у Xtensa GCC PIC-поддержка неполноценная |
| Фиксированный адрес загрузки (как DOS COM) | ломает несколько одновременных приложений [Т-10] |
| Байткод/скрипт | противоречит [Т-9] |

### 3.2 Куда грузится код

**Ограничение, определяющее эту часть: у S3 шины инструкций и данных видят
память через разные окна адресов.** Обнаружено при реализации:

| Память | Окно | Исполнение | Чтение | Запись |
|---|---|---|---|---|
| Внутренняя SRAM, шина данных | `0x3FCxxxxx` | нет | да | да |
| Внутренняя D/IRAM, шина инструкций | `0x403xxxxx` | **да** | **да** | **да** |
| Flash / PSRAM, шина инструкций | `0x42xxxxxx` | да | да | **нет** |
| PSRAM, шина данных | `0x3Cxxxxxx` | нет | да | да |

Цельный образ с одним смещением требовал бы памяти, которая одновременно
исполняемая **и** записываемая через один адрес. Такая память ровно одна —
D/IRAM в окне инструкций, и её мало. Поэтому образ состоит из **двух частей**:
это не оптимизация, а прямое следствие таблицы выше.

| Часть | Что в ней | Куда грузится | Чем ограничена |
|---|---|---|---|
| код | литералы, `.text`, `.hot_rodata`, заголовок приложения | арена в D/IRAM | размер арены, по умолчанию 64 КБ |
| данные | `.rodata`, `.data`, `.bss` | PSRAM через окно данных | свободной PSRAM — мегабайты |
| куча | `ag_mem.alloc` | PSRAM | свободной PSRAM |
| стек | стек задачи приложения | internal SRAM | из манифеста, по умолчанию 16 КБ |

**Константы едут с данными, а не с кодом.** Шрифт, картинка или таблица
исполняться не должны, а арена — самая дорогая память на кристалле, поэтому
`.rodata` попадает в часть данных, где её ограничивает только свободная PSRAM.
Ядру для этого не нужно ничего: код достаёт константу через литерал с абсолютным
адресом, а такое слово релоцируется смещением своей части, как любое другое.
Измерено на приложении со шрифтом 96 КБ: часть кода 212 байт вместо 98 552.
Цена — чтение из PSRAM вместо SRAM (кэшируется) и потеря read-only, которой без
MPU всё равно нет. Исключение объявляется в самом приложении: `AG_HOT_RODATA`
кладёт одну таблицу в `.hot_rodata`, то есть в часть кода и в SRAM, когда
задержка чтения дороже места; `mkaxe.py --rodata code` возвращает старое
размещение целиком.

Части переезжают независимо, поэтому у каждой релокации два признака: в какой
части лежит слово и в какую часть смотрит адрес внутри него. Оба влезли в
младшие два бита смещения — смещения выровнены на слово, эти биты всегда нули.
`mkaxe.py` берёт признак из секции символа и сверяет с уже записанным значением;
несовпадение — ошибка сборки, а не сюрприз на устройстве.

Обмена данными между частями через кэш не требуется: код пишется в internal RAM,
которая стоит перед кэшем и видна обеим шинам, а данные пишутся и читаются через
одну и ту же шину данных. Поэтому этот шаг проверяется без платы.

При этом **ESP-IDF на S3 не отдаёт D/IRAM в кучу**: и `MALLOC_CAP_EXEC`, и
`MALLOC_CAP_IRAM_8BIT` сообщают ноль доступных байт. Поэтому арена кода
резервируется на линковке, в `.iram.bss` — секция NOLOAD, так что арена не
занимает ни байта во flash и не копируется при старте. В адресах она стоит своего
размера всегда, запущено приложение или нет, потому что окно инструкций и окно
данных видят одну и ту же физическую SRAM: по карте линковки рост арены с 16 до
64 КБ забрал у внутренней кучи ровно те же 48 КБ. Размер — параметр сборки
`CONFIG_ARGON_APP_ARENA_KB`, от 4 до 192 КБ.

Что остаётся сделать для приложений с мегабайтами **кода**: положить код в окно
инструкций PSRAM. Это спайк S-1, и ему нужна плата — QEMU здесь не
доказательство, он не моделирует кэш, а на железе перед прыжком нужны writeback
записанных данных и инвалидация кэша инструкций. План Б — R-1 из §11: `.text` в
раздел flash и XIP.

Флаг `hot_text` в манифесте пока ни на что не влияет: код всегда попадает в
арену, то есть в internal SRAM, и это и есть «горячее» размещение. Смысл у флага
появится там, где код целиком в арену не влезает и часть его исполняется из
flash XIP или PSRAM: тогда понадобится сказать, какие именно функции обязаны
остаться в SRAM. У констант «горячее» размещение работает уже сейчас, потому что
по умолчанию они как раз *не* в SRAM — этим и занимается `AG_HOT_RODATA`.

Реализация упирается не в загрузчик, а в формат релокаций, и это стоит знать
заранее: третья область (горячий код, холодный код, данные) даёт девять
комбинаций «в какой части лежит слово × в какую смотрит адрес» вместо четырёх, а
свободных битов в выровненном на слово смещении всего два. То есть это расширение
формата и minor ABI, а не флаг в `if`. На xtensa к этому добавляются два условия:
межобластные вызовы обязаны идти через литералы (обеспечено — `mkaxe.py` форсирует
`-mlongcalls`), а `l32r` читает литерал только назад и не дальше 256 КБ, поэтому у
горячей области должен быть свой пул литералов перед её кодом.

Пока же дешевле оказалось растить арену: эмулятор Mega Drive — 129 КБ кода, и он
целиком лежит в SRAM при `CONFIG_ARGON_APP_ARENA_KB=192`. Цена в том, что арена
резервируется на линковке и общая на все процессы, то есть эти 192 КБ уходят из
внутренней кучи независимо от того, запущено ли что-нибудь. Разбор —
в [`07-emulator-performance.md`](07-emulator-performance.md).

У RISC-V с моделью `medany` код достаёт свои данные PC-относительно, поэтому
расстояние между частями там менять нельзя. Такой образ собирается **слитным**:
обе части в одном блоке, флаг `AG_AXE_CONTIGUOUS` требует от загрузчика положить
данные сразу за кодом и относить обе части одним смещением. Формат при этом тот
же самый.

### 3.3 Структура файла `.AXE`

```
+--------------------+
| AXE header (176 б) |  magic 'AXE1', ABI major/minor, флаги, две части, имя
+--------------------+
| часть кода         |  литералы, .text, .hot_rodata, заголовок приложения
+--------------------+
| часть данных       |  .rodata, .data; bss описан размером, но в файле не лежит
+--------------------+
| таблица релокаций  |  uint32 на слово: смещение | признаки части
+--------------------+
```

Точка входа: `int ag_main(int argc, char **argv)`, её адрес и адрес слота таблицы
ABI записаны в заголовке — искать по имени нечего, символьной таблицы в файле
нет. Ресурсы (иконка, строки, ассеты) появятся позже, под них оставлены
`reserved`-поля.

Заголовок описывает каждую часть четвёркой: адрес линковки, сколько памяти
занять, сколько байт из этого лежит в файле, и где они в файле. Разница между
первыми двумя — это bss, и его обнуляет загрузчик. У части кода она всегда ноль:
код исполняется в том виде, в котором приехал.

## 4. ABI для сторонних приложений [Т-13]

Требование: сторонние разработчики, «какая-то совместимость, но без заморочек».

**Решение: таблица указателей на функции, сгруппированная по подсистемам,
только-дополняемая.**

```c
int ag_main(int argc, char **argv);        // приложение
extern const ag_api_t *g_ag;               // подставляет загрузчик

// внутри libargon:
static inline int ag_open(const char *p, int f) { return g_ag->fs->open(p, f); }
```

Почему не «разрешение символов по именам»: вызов через таблицу — это один
косвенный переход (2–3 такта), никакого оверхеда; при этом ABI становится
**явным объектом**, который нельзя случайно сломать, а не побочным эффектом
экспортируемых символов ядра.

Правила совместимости:

* каждая подтаблица начинается с `uint32_t size` — приложение может проверить
  наличие функции макросом `AG_HAS(api->fs, rename)`;
* новые функции **только в конец** подтаблицы → minor+1;
* новые подсистемы — только в конец `ag_api_t` → minor+1;
* изменение сигнатуры или удаление → major+1 (старые `.AXE` не запускаются с
  внятной диагностикой, а не с крэшем);
* загрузчик проверяет: `app.major == kernel.major && app.minor <= kernel.minor`.

До версии 1.0 major может ломаться; после 1.0 — только с депрекацией на релиз.

Дополнительно доступен `ag_sym(name)` — поиск по имени для необязательных и
экспериментальных API, чтобы не раздувать таблицу.

Полный список подсистем: `sys`, `mem`, `fs`, `con`, `gfx`, `inp`, `dev`, `io`,
`time`, `task`, `proc`, `net`, `res` [Т-14 — «всё»].

## 5. Процессы, многозадачность, снятие зависших [Т-10, Т-11, Т-15, Т-31]

### 5.0 Отзывчивость ввода (инвариант)

**Система обязана оставаться отзывчивой к вводу.** Зависнуть может процесс
приложения; консоль и супервизор не умирают вместе с ним. Горячие клавиши
супервизора (`Ctrl+C`, `Ctrl+\`) принимаются всегда — даже пока приложение или
команда шелла крутятся в долгом I/O.

Практически это значит:

* сбор клавиш и хоткеи живут в отдельных задачах (`console_task`, супервизор), а
  не в том же цикле, что прикладная работа;
* **приложение** на переднем плане проверяет `ag_interrupted()` / `AG_EV_QUIT` в
  длинных циклах; иначе его снимают `Ctrl+\`;
* **builtin шелла** (тот же код, что `fm`, `type`, `copy`, …) работает на задаче
  шелла: `Ctrl+\` к нему не применим. Поэтому долгая работа на задаче шелла
  обязана порционироваться и между порциями (а) показывать, что жива,
  (б) проверять `ag_shell_interrupted()`, (в) при возможности отдавать CPU
  (`ag_yield`). Иначе это баг относительно этого инварианта.

Отмена внутри одного заблокированного syscall (например HostFS RPC на несколько
секунд) — следующий слой; soft-stop срабатывает на границе порции.

### 5.1 Модель

* Одновременно может быть загружено **N приложений** (по умолчанию до 4).
* Ровно одно — **foreground**: владеет консолью и ядром CPU 1.
* Остальные — background: выполняются на core 0 с пониженным приоритетом,
  их вывод уходит в лог, ввод не получают.
  *Реализовано:* своё ядро, свой приоритет, ввод только у переднего плана
  (остальным — `-AG_EPERM`, а не бесконечное ожидание). *Не реализовано:* вывод
  фоновых процессов пока идёт на общий экран, а не в лог.
* Переключение — горячей клавишей (`Alt+1..4`) или командой `fg <id>`.
  *Реализовано:* `fg <pid>` — отдаёт клавиатуру процессу и ждёт его. Горячих
  клавиш переключения пока нет.
* Резидентные службы (аналог TSR) — то же самое, но без консоли.
* `exec()` / `spawn()` доступны приложению [Т-15]: можно запустить дочернее
  приложение и дождаться его завершения (шелл работает именно так).

Многозадачность даётся «бесплатно» — FreeRTOS уже вытесняющий, — поэтому
поддерживается, но конфигурация по умолчанию остаётся DOS-подобной:
одно приложение, одно ядро, максимум скорости.

### 5.2 Потоки внутри приложения [Т-11]

Разрешены: `ag_thread_create()` — тонкая обёртка над задачей FreeRTOS с
привязкой к ядру приложения. Плюс мьютексы, семафоры, очереди, атомарные
операции. Потоки принадлежат процессу и убиваются вместе с ним.

*Реализовано* (`src/proc/threads.c`, подтаблица `task`): до 4 потоков на процесс,
стек 8 КБ по умолчанию (2..32 КБ), приоритет всегда ниже супервизора, выбор ядра
флагами. Мьютексы, семафоры, очереди. `join` — опросом флага, а не семафором:
у FreeRTOS нет join, а семафор корректен только с одним ожидающим.
`critical_enter` — приостановка планировщика на текущем ядре (вложенная), а не
спинлок: спинлок при повторном входе даёт панику вместо ожидаемого поведения.

Всё это учитывается в ресурсном списке. Проверено в QEMU: приложение, которое
завершилось с работающим потоком, незаданным мьютексом и очередью, отдаёт все
четыре ресурса, и внутренняя память возвращается к прежнему значению.

### 5.3 Учёт ресурсов — ключевой элемент надёжности

Каждый процесс имеет **ресурсный список**: все выделения памяти, открытые файлы,
таймеры, зарегистрированные ISR, захваченные устройства, созданные потоки,
сокеты. Любой ресурс, полученный через syscall, регистрируется автоматически.

Это то, чего не было в DOS, и то, что делает возможным пункт [Т-31].

**Как это сделано.** Память — не через список, а через **арену процесса**:
`multi_heap` поверх куска PSRAM, выданного процессу при старте (по умолчанию
1 МБ, `CONFIG_ARGON_APP_HEAP_KB`, или из манифеста). Освобождение всего — это
освобождение арены, то есть одна операция и ноль фрагментации общей кучи. Файлы
— не через список, а по владельцу: у каждого дескриптора VFS записан pid, и
`ag_vfs_close_owned_by(pid)` закрывает всё, что осталось. Списком
(`argon/reslist.h`) учитывается то, что не покрывают эти два механизма: память
вне арены (быстрая, DMA, исполняемая), потоки, таймеры, объекты синхронизации.

Порядок освобождения — по типам: потоки, таймеры, файлы, объекты синхронизации,
память. Не строго LIFO, потому что зависимости именно такие: поток может держать
файл, файл — буфер. Внутри типа — от новых к старым. Список ограничен (32
записи на процесс) и при переполнении **отказывает в вызове**, а не растёт:
достигнутый предел диагностируется, а неограниченный список — это утечка с
лишними шагами.

Побочная выгода, которая обнаружилась сразу: если приложение освобождает
указатель, которого у него нет, это видно — двойное освобождение и чужой
указатель отсекаются до аллокатора и пишутся в журнал.

### 5.4 Снятие зависшего приложения («Ctrl-Alt-Del»)

Супервизор (высокоприоритетная задача на core 0) обрабатывает:

* `Ctrl-C` — мягкий сигнал приложению;
* `Ctrl-Alt-Del` — жёсткое снятие foreground-процесса;
* срабатывание per-process watchdog (приложение не отвечает N секунд);
* необработанный exception внутри процесса (перехват через свой
  panic-handler → определяем виновника по PC/стеку → снимаем только его).

Алгоритм жёсткого снятия:

1. Попросить по-хорошему: выставить процессу признак «просят остановиться».
2. Дать до 500 мс выйти из ядра, проверяя, **держит ли его задача какой-нибудь
   замок ядра** — консольный или файловый.
3. Если держит и после 500 мс — **отказать** в снятии и сказать почему: снятие
   в этот момент обменяло бы зависшее приложение на зависшую систему.
4. `vTaskDelete` всех потоков процесса.
5. Освободить ресурсный список (по типам, внутри типа — от новых к старым),
   арену и образ.
6. Восстановить консоль в текстовый режим, вернуть фокус тому, у кого он был.
7. Записать crash-record в журнал и в `/sys/crash.log` — вместе с хвостом
   журнала, потому что полезная часть разбора обычно не сам отказ, а то, что
   приложение говорило перед ним. Файл пишет супервизор, а не упавшая задача:
   у той мог кончиться стек, или она в шаге от того, чтобы перестать
   существовать. Размер ограничен 32 КБ и по достижении начинается заново —
   система, которая часто падает, не должна забить себе файловую систему.

Три отступления от первоначального замысла, оба измеренные:

* **Флага «внутри ядра» нет.** Вместо него у FreeRTOS спрашивается, кто держит
  мьютекс (`xSemaphoreGetMutexHolder`). Это не стоит ничего на каждом вызове и
  даёт не флаг, который какой-то путь забыл выставить, а факт.
* **Снятие с `tainted`-подсистемой не выполняется, а отклоняется.** Легального
  способа отобрать мьютекс у удалённой задачи в FreeRTOS нет: удаление
  семафора с ожидающими — неопределённое поведение, а пересоздание оставляет
  ждущих на старом хэндле навсегда. Поэтому в этом случае система честно
  сообщает, что нужна перезагрузка, вместо того чтобы делать вид.
* **`Ctrl-Alt-Del` терминал послать не может** — это комбинация локальной
  клавиатуры. Терминальный эквивалент — **`Ctrl+\`** (байт 0x1C), он же
  проверяется в QEMU. И `Ctrl-Alt-Del` при пустом переднем плане **не
  перезагружает** машину, как сделал бы DOS: на промышленной железке случайное
  нажатие не должно уносить систему вместе со всем, что она делала.

`Ctrl-C` — не то же самое: процессу выставляется признак, а сама клавиша
доставляется как событие `AG_EV_QUIT`, так что приложение, заблокированное на
чтении, просыпается и узнаёт о просьбе. Приложение, которое проверяет
`ag_interrupted()`, можно попросить остановиться; приложение, которое не
проверяет, придётся снимать — и это его выбор, а не сюрприз.

> Полной защиты нет и быть не может: без MMU дикая запись по указателю может
> испортить ядро [Т-12 — скорость важнее]. Покрываются типовые случаи: вечный
> цикл, дедлок, исключение, переполнение стека (canary + аппаратный
> stack-guard). Это честный компромисс, он зафиксирован осознанно.

Сделано и проверено в QEMU: вечный цикл (снимается `Ctrl+\`), переполнение
стека (ловит canary FreeRTOS), утечка памяти и незакрытые файлы (возвращаются
целиком), **необработанное исключение** (см. §5.5), **приложение, перестающее
отвечать** (per-process watchdog, см. ниже). **Не сделано:** вывод фоновых
процессов в лог вместо общего экрана; горячие клавиши `Alt+1..4`.

**Per-process watchdog — по заявке приложения, а не по умолчанию.**
`ag_watchdog(ms)` — обещание присылать `ag_heartbeat()` не реже, чем раз в `ms`;
не прислал — супервизор снимает. Навязанный системой срок был бы неверен для
любого приложения, которое законно ждёт долго (клавишу, карту, ответ по шине), а
быть снятым за ожидание хуже, чем не быть под присмотром. Обещание может дать
только сам код, который знает, сколько занимает его работа.

### 5.5 Перехват исключения [Т-31]

Без MMU дикий указатель может дотянуться куда угодно — это зафиксированный
компромисс [Т-12]. Недопустимо другое: чтобы приложение, разыменовавшее ноль,
уносило с собой всю систему. Большинство отказов — вообще не порча памяти:
нулевой указатель, неинициализированный указатель на функцию, промах в приведении
типа. Машина после них полностью здорова, и стоить это должно одного процесса.

Механизм (`src/proc/fault.c`). У Xtensa общие исключения раздаются через таблицу
обработчиков по коду причины, и её контракт — ровно то, что нужно: *«если
обработчик вернул управление, контекст задачи восстанавливается, и всё, что
обработчик изменил в кадре исключения, становится частью восстановленного
контекста»*. Поэтому обработчик подменяет в кадре адрес возврата на адрес
процедуры разбора и возвращает управление. Задача продолжается — в обычном
контексте, на своём стеке, — но уже внутри кода, который пишет crash-record и
завершает процесс.

В обработчике **нельзя ничего блокировать, логировать и выделять**: это
контекст исключения. Он записывает факт в структуру процесса и уходит; всё, что
требует замков, делается в процедуре разбора, которая уже обычная задача.

Обработчик **отступает** в трёх случаях: задача не принадлежит приложению;
приложение уже падало и его разбирают; задача внутри ядра держит замок. Тогда
отказ идёт своим обычным путём — panic-handler с полным отчётом и перезагрузка.
Размотать процесс из-под захваченного замка ядра значит оставить этот замок
захваченным навсегда, то есть обменять упавшее приложение на зависшую систему.

Что попадает в журнал: причина словами, `pc`, адрес обращения, `sp` — и,
главное, **смещение `pc` внутри кода самого приложения**, если он там. Автору
приложения это адрес, который он найдёт у себя, а не абстрактный номер.

Проверено в QEMU: запись по нулю, чтение по нулю, вызов через нулевой указатель
на функцию, и отказ в потоке, а не в главной задаче. Во всех четырёх случаях
приглашение шелла возвращается, `ps` пуст, память возвращена целиком; два отказа
подряд тоже переживаются.

Один случай недостижим по построению: отказ при выключенном кэше flash (например
во время записи во flash) не может даже прочитать этот обработчик и уходит прямо
в panic. Это и правильный исход, и причина, по которой в IRAM живёт panic-handler,
а не он.

## 6. Память [Т-12, Т-30]

* Единое плоское адресное пространство, без защиты.
* Аллокатор ядра — heap ESP-IDF (`heap_caps_*`), но каждое приложение получает
  **свою арену** в PSRAM: `ag_malloc` работает внутри арены процесса
  (аллокатор TLSF), что даёт (а) мгновенное освобождение всего при kill,
  (б) отсутствие фрагментации общей кучи приложениями,
  (в) предсказуемое время выделения.
* `ag_malloc_caps(size, AG_MEM_FAST)` — выделение из internal SRAM для горячих
  данных и DMA-буферов.
* Стек приложения — в internal SRAM, размер из манифеста (по умолчанию 16 КБ).
* Никакого GC, никакого свопа, никакой виртуальной памяти.

## 7. Файловая система [Т-17, Т-18, Т-19]

Единый VFS с точками монтирования:

| Точка | ФС | Назначение |
|---|---|---|
| `/sd` | FAT32/exFAT | приложения, данные, обмен с ПК |
| `/sys` | littlefs (internal flash) | конфиги, журнал, системные файлы |
| `/tmp` | ramfs | временные файлы |
| `/dev` | devfs | устройства |

* Пути POSIX-стиля, длинные имена, регистронезависимое сравнение на FAT.
* В шелле работают DOS-алиасы: `A:` → `/sd`, `C:` → `/sys`, `D:` → `/dev`,
  `T:` → `/tmp`, `\` == `/`.
* Горячее извлечение [Т-18 — «как проще»]: детект по card-detect пину или по
  ошибке транзакции → размонтирование, всем открытым дескрипторам возвращается
  `AG_EIO`, событие в консоль. Транзакционности на FAT нет; журнал ОС пишется в
  littlefs, который power-fail-safe by design.

## 8. Устройства и драйверы [Т-20, Т-21, Т-22]

### 8.1 Модель устройства ✅

Реализовано: `argon/device.h`, `src/dev/`.

```c
struct ag_device {
    char                 name[24];   // "sd0", "flash0", "con", "i2c0"
    char                 driver[24]; // кто это делает: "sdmmc", "builtin"
    ag_dev_class_t       cls;        // BUS/BLOCK/CHAR/DISPLAY/INPUT/SENSOR/...
    uint32_t             flags;      // EXCLUSIVE, HOTPLUG, DMA, READONLY
    const ag_dev_ops_t  *ops;        // open/close/read/write/ioctl/size
    const void          *class_ops;  // vtable класса, отдаётся dev->ops(h)
    void                *priv;
    const void          *owner;      // модуль, зарегистрировавший его
    /* дальше — учёт реестра: сколько открыто, жив ли */
};
```

Две таблицы, а не одна, и это отличие от первоначального наброска. Общая
(`ag_dev_ops_t`) — то, что умеет всякое устройство: открыть, прочитать, записать,
`ioctl`, назвать свою длину. Классовая (`class_ops`) — то, что имеет смысл только
для класса, и её отдаёт `dev->ops(handle)`.

**Устройство — байтовый объект, а положение принадлежит дескриптору.** Это и
позволило одному реестру обслуживать и поток (консоль, которая смещение
игнорирует), и диск (карта, для которой смещение — куда читать), а самим
устройствам — жить в файловой системе как `/dev/имя`. Приложение работает через
`ag_dev_open("sd0")` → handle → `fs->read`/`fs->seek`, либо `ioctl` и классовые
вызовы. Прямой доступ к GPIO/шинам тоже разрешён (`api->io`) — DOS-стиль, полное
доверие.

Почему через файловую систему, а не своей таблицей дескрипторов: таблица одна,
поэтому учёт владельца и закрытие того, что осталось от снятого процесса,
написаны один раз. Вторая таблица была бы вторым местом, где про это забывают.

**Исчезновение** решено так же, как размонтирование носителя: устройство,
которого не стало, пропадает из реестра сразу, а держатель дескриптора получает
`-AG_ENODEV` на следующем вызове. Имя освобождается последним закрытием — иначе
дескриптор на старую карту мог бы дотянуться до новой.

### 8.2 Драйверы [Т-20]

* **Статические** — вкомпилированы в образ и регистрируются на этапе загрузки
  `devices` явным вызовом `ag_dev_register`. Сюда идут базовые: UART, GPIO, I2C,
  SPI, SDMMC, USB, дисплей-ядро, клавиатура. Явный список, а не секция линкера:
  в ESP-IDF своя секция требует фрагмента линкер-скрипта, а выигрыш — только в
  том, что список не надо дописывать; отлаживать явный список проще, и порядок
  регистрации в нём виден.
* **Загружаемые** `.SYS` — тот же загрузчик образов, что и для приложений (не ELF:
  формат `.AXE`, см. §3.3); точка входа `ag_driver_init`, флаг `AG_AXE_DRIVER` в
  манифесте, ABI-версия там же. Могут выгружаться.
* Загружаются по списку из `SYSTEM.CFG` (`DEVICE=/sd/drv/bme280.sys`) или
  вручную командой `drv load`.

**Граница между статическим и загружаемым не вкусовая.** Контроллер внутри SoC —
Wi-Fi, BT, USB host, SDMMC, I2S, LCD, camera — это стек ESP-IDF в десятки и сотни
килобайт с прерываниями, DMA и своими задачами; вынести такое в модуль значит
вынести половину IDF, поэтому оно статическое. Микросхема **на** шине — датчик,
расширитель портов, контроллер дисплея, RTC, драйвер моторов — это килобайты кода
про регистры одного чипа, и это `.SYS`. Ровно так делил DOS: BIOS плюс `DEVICE=`.

Отсюда следует то, ради чего это и задумано: **одна универсальная сборка** со
всеми контроллерами и шинами внутри, а конкретная периферия конкретной платы
доводится драйверами, принятыми по UART, Wi-Fi или BLE, без пересборки прошивки.
Код загруженного модуля лежит в арене, то есть в internal SRAM, а значит его
обработчик прерывания законен — в отличие от кода в PSRAM. План и цена — фаза 4.5
в [04-roadmap.md](04-roadmap.md); там же названо главное требование, без которого
это не промышленное решение, а дыра: приём кода должен быть режимом, в который
входят намеренно, с подписью образа и записью в журнал.

### 8.3 Периферия v1 [Т-21]

Базовые (статические): GPIO, UART, I2C master/slave, SPI, SDMMC/SD-SPI,
TWAI(CAN), RS-485/Modbus RTU, 1-Wire, LEDC/PWM, MCPWM, ADC/DAC, RMT, I2S,
USB host (HID/MSC) + device (CDC/MSC), RTC, timers, Wi-Fi/Ethernet (§9).

Дисплей [Т-21, Т-25]: ядро определяет абстракцию `display` (fb, разрешение,
формат, flush-регион); конкретные контроллеры (ILI9341, ST7789, SSD1306,
RGB-панели, MIPI-DSI на P4) — драйверы, статические или загружаемые. Тип и пины
берутся из `BOARD.CFG`, поэтому неизвестная плата поднимается без пересборки.

**Что именно остаётся в прошивке, а что уезжает в модуль** — граница проходит не
по «дисплею» целиком, а внутри него:

| Слой | Где | Почему |
|---|---|---|
| Движок интерфейса: SPI/QSPI с DMA, LCD_CAM в режимах RGB и i80, тайминги, bounce-буферы | прошивка | десятки килобайт IDF, прерывания, DMA, точные тайминги |
| Панель на SPI/I2C: последовательность инициализации, команды окна, поворот, формат пикселя | **`.SYS`, и почти целиком данными** | панели различаются таблицей команд, а не алгоритмом |
| RGB-панель | **`BOARD.CFG`, без кода** | различия — это тайминги (hsync/vsync/porch) и пины |
| Сенсор камеры: регистры по SCCB, режимы, форматы | **`.SYS`** | это таблицы регистров одной микросхемы |
| Захват DVP: LCD_CAM в режиме камеры, DMA в PSRAM, VSYNC/HREF | прошивка | то же, что и выше: DMA и прерывания |

Отсюда важное следствие для загружаемых драйверов панелей: **они получаются
почти без кода.** Драйвер ST7789 — это геометрия, коды команд `CASET`/`RASET`/
`RAMWR` и список init-команд; работу с шиной делает движок. А поскольку константы
образа живут в части данных, эти таблицы **не занимают арену кода** вовсе — в ней
остаётся килобайт-два логики на панель.

**Чего «драйвер в прошивке» не даёт.** Универсальная сборка содержит все
*интерфейсы*, какие есть у чипа, а не знание о каждой панели, и это не одно и то
же. На S3 не заработает ничего из этого, сколько бы кода ни добавить:

* **MIPI-DSI** — интерфейса нет в кремнии (он есть у P4);
* панели и сенсоры с **MIPI-CSI** — по той же причине; камеры только DVP,
  8-битный параллельный;
* **RGB-панели за пределами полосы PSRAM**: кадровый буфер живёт в PSRAM, и
  800×480×2 при 60 Гц — это уже ~46 МБ/с только на скан, то есть край для octal
  PSRAM на 80 МГц; 1024×600 — за краем;
* панель, которой нужны **свои напряжения или своя последовательность питания**,
  без соответствующей обвязки на плате.

Всё остальное — вопрос таблицы инициализации и пинов, то есть данных, а не
пересборки прошивки.

### 8.4 Привязка [Т-22]

`SYSTEM.CFG`/`BOARD.CFG` — основной источник истины. Опциональный `probe`:
сканирование I2C/1-Wire/USB и подбор драйвера по таблице ID. `probe` появится
после `api->io`: до него сканировать нечем.

## 9. Консоль, графика, сеть [Т-24..Т-27]

### 9.1 Консоль-мультиплексор

Требование: работать и headless (UART), и с дисплеем+клавиатурой, и по telnet —
одинаково.

**Решение: ядро держит виртуальный текстовый экран** (сетка ячеек «символ +
атрибут», размер из конфигурации, по умолчанию 80×25) — прямая аналогия
видеопамяти DOS. К нему подключаются endpoint'ы:

```
                       ┌─ UART/USB-CDC  ← рендер VT100
virtual text screen ───┼─ telnet        ← рендер VT100
      80×25            └─ local display ← рендер шрифтом в framebuffer
                     ▲
входные события ─────┘  USB HID клавиатура | PS/2 | VT100-парсер с UART/telnet
```

Все endpoint'ы видят одно и то же и могут вводить. Приложение пишет в консоль
одним API и не знает, куда это уходит.

**Ввод и поток данных.** События ввода идут через очередь (64 события), и
консоль читает из порта не больше, чем очередь готова принять: непрочитанное
остаётся в буфере порта, где оно в безопасности. Этого мало, и вот почему это
выяснилось на практике: пока приложение или `recv` не успевает разбирать
события, буфер порта заполняется, и драйвер начинает **терять байты молча**. Для
человека, который печатает, это незаметно; для файла, который приезжает командой
`recv`, это файл, который тихо неверен — худший из возможных исходов.

Поэтому:

* консоль **вычитывает порт до конца в пределах такта**, а не один блок в 10 мс:
  64 байта за такт — это 6.4 КБ/с, то есть *ниже* скорости линии на 115200, и
  всплеск гарантированно переполнял буфер;
* когда очередь заполняется наполовину, консоль посылает **XOFF**, а когда
  освобождается на три четверти — **XON**. Это то, для чего они существуют, стоит
  двух байт, и понимается любым терминалом. Байты, уже находящиеся в полёте,
  принимает буфер порта (2 КБ ≈ 180 мс линии).

Обвязка тестов уважает XOFF, вырезает эти два байта из транскрипта (это сигнал
линии, а не содержимое экрана) и сверяет число байт, о котором отчитался `recv`,
с размером отправленного файла.

### 9.2 Графика [Т-25]

По умолчанию — текст. Приложение может запросить графический режим:
`ag_gfx_acquire()` → получает framebuffer локального дисплея, текстовый рендерер
на нём приостанавливается (удалённые консоли продолжают работать в тексте).
`ag_gfx_release()` — экран перерисовывается. Это ровно модель смены видеорежима
в DOS.

Ядро даёт: framebuffer, flush, базовые примитивы (rect/blit/text/line) и
шрифты. Полноценный GUI — библиотека в SDK, **не в ядре**.

### 9.3 Системные утилиты [Т-26]

Встроены в образ ОС, не файлы на карте: `dir cd copy del ren md rd type cls ver
mem ps kill run fg drv dev cfg mount format date time echo more hexdump reboot
help`. Плюс сетевые (§9.4) во второй фазе.

Туда же **файловый менеджер** (`fm`, `apps/fm`): по тому же принципу — плата,
которая загрузилась, должна уметь показать свои диски без того, чтобы на неё
сначала что-то положили. Тот же исходник собирается и как загружаемый `.AXE`;
встроенный вариант вызывает те же функции таблицы ABI, что и загруженный, поэтому
контракт проверяется, а не обходится.

**ZIP (принято 9 августа 2026, сделано):** в ядро — **`unzip`** (list/extract,
store/deflate, miniz в `third_party/miniz`). **`ZIP.AXE`** — create/update (store)
и list/store-extract на карте; deflate-extract — через builtin.

### 9.4 Сеть [Т-27]

Отложена до фазы 3, но заложена в ABI (`api->net` может быть NULL, приложение
проверяет). План: Wi-Fi STA/AP, Ethernet, BSD-сокеты, DNS/SNTP, telnet-сервер
консоли, FTP/HTTP сервер для доступа к SD, MQTT, Modbus TCP, OTA.

### 9.5 Безопасность [Т-28, Т-29]

Secure boot, шифрование flash, подпись приложений, песочница — **не в v1**.
Приложениям полное доверие. Формат `.AXE` содержит зарезервированное поле под
подпись, чтобы добавить это позже без слома совместимости.

## 10. Бюджет ресурсов [Т-30]

Цель «5%» уточняю честно: на S3/8 МБ PSRAM «5% всего» — это ~410 КБ, что легко.
Дефицитный ресурс — **internal SRAM (512 КБ)**, и вот бюджет по нему:

| Компонент | Целевой бюджет SRAM |
|---|---|
| ESP-IDF + FreeRTOS (неустранимо) | ~45 КБ |
| Ядро ArgonOS (proc, mem, vfs, dev, loader) | ≤ 24 КБ |
| Консоль (текстовый экран 80×25 + рендер) | ≤ 8 КБ |
| Шелл | ≤ 6 КБ |
| FAT + littlefs + буферы | ≤ 24 КБ |
| USB host стек | ≤ 20 КБ |
| Wi-Fi + lwIP (когда включены) | ~60 КБ |
| **Итого без сети** | **~127 КБ (25% SRAM)** |
| **Свободно приложению (без сети)** | **~385 КБ SRAM + вся PSRAM** |

Целевые показатели:
* время от reset до приглашения шелла: **< 400 мс** (без Wi-Fi);
* оверхед syscall: **< 20 нс** (косвенный вызов);
* латентность прерывания приложения: **< 5 мкс** [Т-23 не задан — берём как цель];
* джиттер задачи приложения при пустом core 1: **< 10 мкс**.

Все цифры проверяются автотестом `bench` и печатаются командой `mem` / `bench`.
Регресс бюджета — повод для отката изменения.

### Подтверждённое ограничение: окно внешней памяти 32 МБ общее

У ESP32-S3 шина данных адресует внешнюю память единым окном **32 МБ, общим для
flash и PSRAM**. Обнаружено на практике: при 32 МБ PSRAM `spi_flash_mmap`
возвращает `ESP_ERR_NOT_FOUND` («no such vaddr range»), а вслед за ним
`esp_partition` не находит **ни одного** раздела — потому что читает таблицу
через отображение, а не чтением. Симптом при этом выглядит как «сломана
таблица разделов», хотя `esp_flash_read` по тому же адресу отдаёт корректные
данные.

Следствия:

* модуль с 32 МБ PSRAM не оставляет адресного пространства под flash —
  такие платы для ArgonOS непригодны;
* 8 МБ (N16R8) и 16 МБ — рабочие конфигурации;
* арена исполняемого кода приложений (§3.2) тоже берёт адреса из этого окна,
  так что её размер конкурирует с отображением flash. Учтено: арена по
  умолчанию 2 МБ, настраивается в `SYSTEM.CFG`.

В QEMU по этой причине эмулируется 8 МБ PSRAM, а не 32.

Каждый риск закрывается отдельным micro-benchmark'ом до того, как на нём будет
построена подсистема.

## 13. Организация проекта

* Лицензия: **ядро GPL-3.0-or-later**, **SDK/ABI Apache-2.0** [Т-35] — copyleft
  на ядро (форки с распространением остаются открытыми); публичный syscall ABI
  пермиссивный, чтобы приложения могли быть любой лицензии, включая закрытую.
  GPL-3.0 выбран из‑за совместимости с ESP-IDF (Apache-2.0). См. `LICENSING.md`.
* Код и комментарии — английский; проектная документация — русский (перевод
  перед публичным релизом).
* Стиль: C11, ядро без исключений и динамического C++.
* Сборка: ESP-IDF ≥ 5.3, CMake, `idf.py`.
* Разработка ведётся под Windows, поэтому в путях запрещены зарезервированные
  имена устройств: `con`, `aux`, `prn`, `nul`, `com1..9`, `lpt1..9`. Git молча
  пропускает такие каталоги — консольная подсистема живёт в `src/console/`,
  а не в напрашивающемся `src/con/`.
* Тесты: host-тесты чистой логики (ELF-парсер, VFS-пути, конфиг, аллокатор)
  собираются обычным GCC и гоняются в CI без железа; hardware-in-the-loop —
  когда появится плата [Т-38].

См. `docs/04-roadmap.md`.
