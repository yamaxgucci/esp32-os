# 07. Больше мощности и периферии: собрать кластер из нескольких плат

Эта глава — для случая «у меня есть плата, я ею пользуюсь, и мне стало мало».
Больше ядер, больше экранов, больше ЦАПов и карт: вторую плату можно подключить
проводом, и она станет продолжением первой — без сети, без роутера и без единой
строчки кода с вашей стороны.

Что при этом происходит по сути: **платы остаются самостоятельными**, у каждой
свой экран, своя файловая система и свои программы. Провод даёт три вещи:
дальнему узлу можно передать файл, на дальнем узле можно запустить программу,
и его устройства (`cyd.lcd0`, `zero.pcm0`) видны как свои. Плюс, если плат три,
средняя пересылает кадры между крайними — тогда крайние видят друг друга.

## Что нужно физически

* Вторая плата с ArgonOS и свободный UART на обеих.
* Три провода: `TX` одной платы → `RX` другой, `RX` → `TX`, и земля. Питание
  отдельное: UART им не делится.
* Если плат три и вы хотите, чтобы крайние видели друг друга, — **средняя** должна
  иметь два свободных UART. Середина выбирается не настройкой, а тем, у какой
  платы два провода: та и есть середина.

## Шаг 1. Дайте платам имена

Имя — это адрес, по которому к плате обращаются, и оно должно пережить
перезагрузку. В `SYSTEM.CFG` на каждой плате:

```
[cluster]
name = cyd
```

Буквы, цифры, `-` и `_`, до 8 знаков, без точки (точка отделяет узел от
устройства в `n2.pcm0`). Если имя не задать, плата возьмёт его из своего чипа —
уникальное, но нечитаемое.

## Шаг 2. Провода и скорость

В `SYSTEM.CFG` каждой платы — какой UART куда смотрит:

```
[link]
uart = 1
baud = 460800
bind = auto
```

`bind = auto` привязывает **все** провода, которые есть у платы: у середины их
два, и это нормально.

```
[link2]
uart = 0
baud = 460800
```

**Скорость на обоих концах провода обязана совпадать.** Несовпадение выглядит
коварно: байты приходят, а кадры не собираются ни один, и `link` честно пишет
`this node is c3, the other is not saying yet`. Ровно так это и выглядит на
практике — «провод вроде живой, а соседа нет».

Скорость выбирайте по замеру, а не по максимуму. На нашей разводке провод
уверенно живёт на 460800 и сыпет на 921600 (36 битых кадров и 597 пропусков на
19 КБ против 6 и 54), причём файл доезжает в обоих случаях — просто на 921600
провод занят переспросами.

## Шаг 3. Драйвер провода

В `modules.txt` платы должен быть её драйвер провода:

* `NODELN32.SYS` — ESP32 (CYD),
* `NODELINK.SYS` — ESP32-S3 (Zero),
* `NODELNRV.SYS` — RISC-V (C3).

Драйвер лежит в образе `C:` (в `c:\drv`), а не в прошивке ядра. Отсюда правило,
которое стоит запомнить: **правка драйвера требует двух прошивок** — образа `C:`
и ядра. И порядок важен: **сначала `C:`, потом ядро**. Если наоборот, новое ядро
примет старый драйвер (он просит более старый ABI) и вызовет его по новой
таблице — молча и неправильно. В обратном порядке старый драйвер просто
откажется грузиться и скажет об этом.

## Шаг 4. Образы, которые смогут исполнить соседи

Правило простое: **плата носит образы, которые могут исполнить её соседи**.
Программу на дальний узел отправляет тот, кто просит, — значит нужный образ
должен лежать у просящего. Списки — в `apps.txt` платы; наборы сборок готовит
`tools/mksysfs.py`.

Если плата через один переход (крайние в тройке), ей нужны образы **обеих**
архитектур соседей: сегодня у Zero в `apps.txt` лежат и RISC-V сборки для C3, и
Xtensa LX6 для CYD. Когда такого образа нет, дальняя программа не запустится не
из-за провода, а из-за отсутствия файла — и это видно в журнале дальнего узла.

Удобно, что подмена работает сама: если на середину пришёл образ под чужой
набор команд, она берёт **свою** сборку той же программы по имени и запускает её
(`node: /node/sys/xeno32.axe is for another processor; running my own`).

## Шаг 5. Настроить плату — и прошивка тут не нужна

**Если ArgonOS уже стоит на обеих платах, прошивать нечего.** Всё, что до сих
пор перечислено, — это файлы на работающей плате, и кладутся они туда без
кабеля и без сборки:

* `SYSTEM.CFG` (`[cluster] name`, `[link] uart/baud/bind`, `[modules]`) правится
  на самой плате — в шелле есть редактор, а `SYSTEM.CFG` читается при загрузке;
* драйвер провода — это файл в `c:\drv`, а `[modules]` в `SYSTEM.CFG` просто
  называет его; файл можно залить на плату через `recv` по консоли или забрать
  у соседа через `link get`;
* программы (`*.AXE`) — тоже просто файлы; `apps.txt` нужен только сборщику
  образа `C:`, на самой плате его никто не читает.

Отсюда весь пользовательский путь: **имена → провода и скорость → драйвер в
`[modules]` → образы, которые смогут исполнить соседи → `link nodes`**. Ни
`argon build`, ни `mksysfs` в нём не встречаются.

Прошивка нужна в двух случаях, и оба — не про ежедневное использование:

1. **На голую плату ставится сама ОС** (первый раз). Тогда образ пишется
   целиком — ядро и `C:`:

   ```
   argon.cmd target esp32s3-zero      # слово платы, не чипа
   argon.cmd build
   argon.cmd apps -All                # полный манифест: пакам нужны образы из core
   python tools\mksysfs.py --board boards\esp32s3-zero --flash -p COM6
   argon.cmd flash -port COM6 -NoMonitor
   ```

   `target` сносит `build/` целиком, поэтому `apps` нужно запускать **после**
   `build`. Для C3 образ `C:` берите из пака без радио (в репозиторном паке
   `AUTOEXEC.BAT` содержит `telnet on`, а радиовещания в этом образе нет — плата
   уходит в петлю перезагрузок; для платы, которую действительно настраивают на
   Wi-Fi руками, этот пак правильный).

2. **Обновляется сама ОС** — ядро или драйвер провода. И даже это не обязано
   быть кабелем: в шелле есть `ota` (обновление по сети), а соседняя плата умеет
   быть программатором — на Zero лежит `ESPFLASH`, который говорит с
   ROM-загрузчиком C3 по проводу, ровно для платы без своего кабеля данных.

Порядок «сначала `C:`, потом ядро» относится только к случаю 2 и только к
драйверу: ядро и драйвер связаны версией ABI, и записанные в обратном порядке
дают смешанную пару, которая работает неправильно молча.

## Шаг 6. Проверьте, что соседи видят друг друга

На каждой плате:

```
link nodes
```

Ожидаемое: у платы с одним проводом — она сама и сосед, а под ними строка
`beyond them, seen through a neighbour ... zero 2 cores via c3`; у середины — все
три. Потом двусторонний тест провода: на одной `link echo 20`, на другой
`link ping 8` — должно вернуться `8 of 8`.

## Шаг 7. Работа с дальним узлом

```
link use zero          # выбрать, с кем говорить: имя соседа или дальнего узла
link                   # что выбрано и как себя чувствует провод
link get c:\prog.axe c:\local.axe    # забрать файл у дальнего
link run c:\prog.axe                 # запустить у дальнего (образ берётся у вас)
ps                     # таблица процессов всей тройки, дальние строки как zero.1
kill zero.1            # остановить дальний процесс
dev                    # устройства, включая одолженные: cyd.lcd0, zero.pcm0
```

Устройства дальнего узла доступны по имени `<узел>.<устройство>` — можно вывести
картинку на экран CYD или отдать звук на ЦАП Zero, не думая о том, что это другая
плата.

## Грабли, которые мы измерили

* **Разная скорость на концах провода** — самый частый случай «соседа нет».
* **`telnet on` в `AUTOEXEC` без сети** — плата уходит в петлю панических
  перезагрузок (на RISC-V утверждение lwIP — это паника). Лечится либо образом с
  радио, либо строкой без `telnet`.
* **Память середины** — самый тесный ресурс. Один гость на 8 КБ оставляет
  ~26/17 КБ, второй помещается впритык, а круговой рейс гостя домой оставляет
  ~32/9 КБ. Если что-то не запускается «на середине», смотрите `mem` и
  `no memory for a N byte task stack` — это не провод.
* **Замер по консоли**: экран перерисовывает приглашение, пока команда ещё
  работает. `dir`, снятый сразу после «приглашения», покажет недописанный файл;
  дождитесь последней строки самой команды.
* **Открытие консоли C3 через USB сбрасывает чип** (`reset: usb-serial-jtag`), и
  после сброса имена соседей переучиваются за один обмен. Это нормально; но если
  инструмент открывает порт, он делает сброс.

## Сколько плат можно

До четырёх проводов на плату. Каждый провод — это отдельная задача-читатель,
поэтому «просто добавить ещё один сосед» стоит памяти; на маленькой RISC-V плате
это заметно. Форма, которая окупается: звезда или цепочка, где середина отдаёт
свои устройства и ядро, а крайние работают сами.
