# The ESP32-A1S Audio Kit

The board the amplifier emulator is meant to live in: an AI-Thinker ESP32-A1S
Audio Kit marked **V2.2 A404**, with an ES8388 codec, a guitar jack, a
headphone jack and no screen at all.

Everything below was measured on the board on this desk.

## Getting to it

Plug an ordinary USB cable into the micro-USB marked **UART**. The one marked
`power` carries no data.

Windows Update has no driver for its CP2102: the device sits at code 28,
`CM_PROB_FAILED_INSTALL`, and no COM port appears. Install Silicon Labs'
universal VCP package and it becomes **COM12**. Auto-reset works, so flashing
needs no BOOT button.

## Two targets, and why

```
argon target esp32-a1s        the pedal: no radios, the emulator at its fastest
argon target esp32-a1s-net    the same board with Wi-Fi, so a phone can be its screen
```

They exist because of one number. The emulator is 57868 bytes of code that
runs on every one of 22050 samples a second, and whether it fits the code
arena decides whether it executes from RAM or through the flash cache:

| | emulator, 2x + 45 ms cabinet |
| --- | --- |
| arena too small, flash XIP | 168% of the audio block |
| arena large enough, RAM | 70% |

Wi-Fi wants most of the instruction RAM the arena lives in, so the networked
target buys it back: `-Os` for the firmware, silent assertions, no
coexistence, no WPA3, and `CONFIG_HEAP_PLACE_FUNCTION_INTO_FLASH`. That gets
the arena to **60 KB, which is the ceiling** — 68 overflows by 7264 bytes.

Read the map before trying to find instruction RAM by guesswork. Of 120269
bytes, 49152 are the arena itself and the rest is FreeRTOS, the PHY, the flash
driver, esp_hw_support, the HAL and the heap. Turning off CAN, 1-Wire, RMT,
MCPWM, Modbus, MQTT, SSH, TLS, telnet, SNTP, ESP-NOW, OTA, USB host and the
camera changed the total by **zero bytes**: none of them was ever resident.

### Drivers go in flash here

`[modules] xip = 1` in SYSTEM.CFG. Drivers load at boot, before any
application exists, so PHONE.SYS's 23 KB would take the arena and leave the
emulator's 57 KB to flash. A driver pushing pixel bands does not notice; the
thing running on every sample does.

## What it costs, measured

Against 11609 us of audio in a block (22050 Hz, 256 frames), with the curves
in internal memory:

```
of 11609 us a block: waiting for input 973, valves 5137, cabinet 2987,
                     the rest 26 (9125 total)
```

| | us | % of the block |
| --- | ---: | ---: |
| valves 1x + ADAA | 2753 | 23 |
| valves 2x + ADAA | 5430 | 47 |
| valves 4x + ADAA | 10677 | 91 |
| cabinet, 45 ms, 4 parts | 2880 | 25 |
| the plumbing around them | 27 | 0 |

So **2x with a cabinet fits with room and 4x does not**. Measured on the
radio-less target, which is the fastest this board goes:

| | valves | cabinet | total | |
| --- | ---: | ---: | ---: | --- |
| 2x, 45 ms cabinet | 5234 | 2696 | 7961 (69%) | no drops, no resyncs |
| 4x, 45 ms cabinet | 9347 | 2915 | 12293 (106%) | 213 resyncs |
| 4x, 30 ms cabinet | 9294 | 2681 | 12007 (103%) | 169 resyncs |
| 4x, 23 ms cabinet | 9311 | 2606 | 11950 (103%) | 148 resyncs |

**Shortening the cabinet does not buy 4x, and barely buys anything at all.**
23 ms costs 2606 us against 45 ms at 2696: the partitions are not the cost,
the transform is, and it is paid once a block whatever the impulse length. So
use the long one - 45 ms keeps the low end that 23 throws away, for 3% of a
block.

On the S3-Zero the same 4x costs 63%, which is the LX7 against this LX6. If 4x
is wanted, it is wanted on a different chip.

The radio costs about three points of the block on top of everything else: 69%
without it against 72% with the point up.

Two traps in reading those numbers:

* `bench` runs the chain forty times over the same buffers, so the tables stay
  in cache and it under-reports — by 17% on the valves and 70% on the cabinet.
  The block loop times its own parts for that reason.
* With a guitar plugged in, `ag_pcm_read` blocks until the converter has a
  block. That wait is not work, and counting it as work made a 79% chain read
  as 100%.

### The curves go in one block per stage

The table is 96 KB; internal memory has 133 KB free and a largest block of 76.
Asked for whole it lands in external memory and every lookup goes there — 6894
us against 5453 for the valves. `ag_amp_build_split` takes one pointer per
stage, 24 KB each, which fit where one 96 KB block does not. Same floats, same
order.

## Faults of the board itself

**The microphones cannot be switched off.** LINEIN L/R are wired to LIN2/RIN2,
which are also MIC2's pins, so the second microphone is in the signal whatever
the codec is told to select. It is a known AI-Thinker fault and somebody has
reported it on this exact marking. The repair is to lift **C19 and C20**.
`stomp ... inmix` adds the two input channels on the theory that the
microphone arrives inverted on the right; it did not help here, so it is
offered and not relied on.

**The access point is worth 20 dB of the input's noise floor.** Measured with
LOOPBACK.AXE and a cable from the output jack to the line input, nothing
playing:

| | in peak | in rms |
| --- | ---: | ---: |
| point up, driver defaults | 455 | 40 |
| point up, `beacon_ms 500`, `txpower 8` | 330 | 30 |
| radio off (`wifi off`) | 17 | 3 |

It is heard as a knock at the beacon rate. The two settings recover about
2.5 dB of it; the rest is the radio being powered at all, and nothing in
software reaches it.

`wifi off` gives the quiet input back at once - but nobody can type `wifi on`
into a phone that went away with the network, so there is:

```
wifi quiet 300
```

The radio stops, the console it was typed on disappears with it, and five
minutes later the point comes back from SYSTEM.CFG by itself. It runs on the
shell's own task, which survives its console.

It blocks that shell for the duration, so the working order is a slot each:
**Alt+1** runs the amplifier, **Alt+2** is a shell, and `wifi quiet` goes in
the second one. Set the knobs with the point up, then quiet it and play.

## The codec

An ES8388 at 0x10 on i2c0 (sda 33, scl 32). Pins in
`boards/esp32-a1s/BOARD.CFG`: mclk 0, bclk 27, ws 25, dout 26, din 35, and
`audio.i2c = 0` so the kernel raises the bus before the codec is programmed.
`display.driver = none` matters: without it the system reaches for a 640x400
framebuffer and the whole devices stage fails with -12.

**Restart the digital engine after moving the word clock.** Writing
DACCONTROL21 (0x2B) and leaving the decimator and state machine running gives a
codec that works on every other open — alive, dead, alive, dead, six opens
running, and it survives a board reset because the ES8388 has its own supply
and EN does not reach it. Two writes fix it:

```c
{ES_CHIPPOWER, 0xf0}   /* stop the decimator and the state machine */
{ES_CHIPPOWER, 0x00}   /* and start them again on the clock just chosen */
```

Espressif's own `es8388_start` has always done this. A day was spent bisecting
firmware settings by ear before anybody read a driver that works.

## Hearing it without a person in the room

`LOOPBACK.AXE` plus a 3.5 mm male-male cable from the output jack to the line
input. It plays a tone, reads the same device back, and prints the level,
the returned frequency and twelve raw samples:

```
loopback: out 80%, in peak 18630 rms 12880 of 32767, 440 Hz back
```

Always run the control with the cable out - 18 against 18630 - or the number
proves nothing: the codec has analogue paths between its input and output
sections and could be hearing itself.

## Running it

```
run c:mp.bat     the guitar, live
run c:	ake.bat    the recorded take instead, for measuring
```

They are `boards/esp32-a1s/AMP.BAT` and `TAKE.BAT`, and each is one line with
the reasons above it:

```
run c:\STOMP.AXE jcm800 os 2 cabms 46 cab c:\CAB.WAV inmix out pcm0
run c:\STOMP.AXE jcm800 os 2 cabms 46 cab c:\CAB.WAV play c:\DI.WAV out pcm0
```

The take is the same three seconds every time, so two runs can be compared; a
load figure taken with a guitar is a figure about what was played.

`in`/`inmix` takes the guitar instead of the take. The cabinet is
`assets/audio/guitar-di/1 Vox AC30 1.wav` resampled to 22050; `cabms`
truncates it, and on this board 45 ms costs 25% of the block against 150 ms
costing three times that.
