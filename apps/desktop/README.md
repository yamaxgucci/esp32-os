# DESKTOP.AXE — графическая оболочка в стиле Windows 3.11

Рабочий стол, окна, папки, файлы, мышь. Загружаемое приложение, **не часть
прошивки**: ядро об оболочке не знает.

План, принятые решения и список того, чего здесь сознательно нет —
[`docs/plans/desktop.md`](../../docs/plans/desktop.md). Читать его первым.

**Состояние: этап 2 из 4, наполовину.** Готово всё от этапов 0 и 1 плюс:
значки 16×16, диски на столе из `mountinfo`, окно папки со списком (значок,
имя, размер с разрядкой), полоса прокрутки со стрелками, выделение, вход в
подкаталог и выход по `..`, клавиши (стрелки, PgUp/PgDn, Home/End, Enter,
Backspace, F5), песочные часы на время чтения каталога, «Выполнить…» с вводом
строки.

**Что не работает: запуск программы.** Образ загружается и получает экран —
GFXDEMO рисует, — но **не получает ввода**, и вывод консольной программы не
доходит до транскрипта. Значит, отданный экран нельзя попросить обратно
клавишей. Разбор ниже, в «Запуск: экран отдаётся, ввод нет». Файловых
операций (копировать/переместить/удалить) ещё нет — это этап 3.

## Сборка и запуск

```
argon apps --only DESKTOP.AXE
argon run -Gfx -HostFs build\sd_card
```

В госте:

```
run h:\desktop.axe            Esc или Q — выход
run h:\desktop.axe 30         то же, но выйдет само через 30 секунд
```

Число секунд — для скриптов: приложение никогда не остаётся висеть. `-Gfx`
обязателен: без него у эмулятора нет RGB-панели и рисовать некуда.

| Клавиша | Что делает |
|---|---|
| `Ctrl+Tab` | следующее окно |
| `Ctrl+F4` | закрыть активное окно |
| `Alt+F4` | выйти из оболочки (спросит) |
| `F10` | встать на строку меню; стрелки, `Enter`, `Esc` |
| `Esc`, `Q` | выход, если клавишу больше никому не нужно |
| `F5` | перерисовать весь экран |
| `F6` | послать кадр заново, ничего не рисуя |

**`Alt+Tab` и `Alt+1..4` брать нельзя** — их забирает супервизор для слотов
сессий, и забирает раньше, чем приложение их увидит. Поэтому окна
переключаются `Ctrl+Tab`, а закрываются `Ctrl+F4`: в Windows 3.11 это ровно
те же сочетания для окон *внутри* приложения, так что ничего не выдумано в
обход. Оболочка, которая повесила бы свои окна на `Alt+Tab`, выглядит
работающей до первого нажатия, а потом отдаёт экран пустому слоту с
приглашением шелла — что и случилось при первом прогоне сценария.

Мышью: тянуть за заголовок, тянуть за край или угол — изменить размер,
двойной щелчок по заголовку — развернуть и обратно, кнопки в заголовке —
системная (закрыть), свернуть, развернуть, двойной щелчок по плитке
свёрнутого — вернуть, двойной щелчок по столу — новое окно.

`F6` — не украшение. Он отличает два отказа, неразличимых на снимке: пиксели,
которых оболочка не нарисовала, от пикселей, которые она нарисовала, а до
панели они не дошли.

## Проверка без рук

```
.\apps\desktop\check.ps1                        # поверхность по умолчанию
.\apps\desktop\check.ps1 -Width 320 -Height 240 # размер, как на платах
```

Поднимает QEMU с RGB-окном, запускает оболочку, водит указателем по экрану,
щёлкает, снимает PNG, нажимает `F5`, снимает второй PNG и сравнивает их.
Числа берутся не с картинки, а из транскрипта: сколько событий указателя и
клавиш дошло, был ли фокус, сколько было перерисовок.

Что именно проверяется и почему — в шапке `check.ps1`. Главное там —
**сравнение двух снимков**: по одному снимку нельзя понять, что часть
нарисованного не доехала до стекла.

Раздел **C: печётся в образ прошивки** (`tools/mksysfs.py`, потом
`qemu-boot.ps1 -SysFs`), поэтому весь прогон — одна загрузка: размер
поверхности лежит в `SYSTEM.CFG` до старта, драйверы уже в `C:\DRV` и
перечислены в `[modules]`, сама оболочка на C:. Гость ничего не пишет во
флеш и не перезагружается. Это не аккуратность: очевидный вариант — записать
`C:\SYSTEM.CFG` из шелла и перезагрузиться — проверен и для теста не годится
(на восьми прогонах трижды файл читался обратно битым, `-91`, и загрузка
после такой записи занимала 128 секунд вместо двух).

Сценарий этапа 2: двойной щелчок по значку диска открывает окно на его
корне, двойной щелчок по каталогу входит в него, двойной щелчок по `..`
выходит, снимок, `F5`, второй снимок, выход. **Запуск программ в проверке
пока не утверждается** — см. «Запуск: экран отдаётся, ввод нет».

Прежний сценарий этапа 1: открыть из меню четыре окна, `Ctrl+Tab` туда и обратно,
поднять первое щелчком по заголовку, свернуть его кнопкой, вернуть двойным
щелчком по плитке, протащить обводкой, снять снимок, `F5`, снять второй,
закрыть два окна `Ctrl+F4`, выйти. Три прогона (640×400 дважды и 320×240):
48–50 событий указателя, 8 клавиш, 2 перерисовки, **2 окна осталось**,
37 пикселей различия между снимками (цифры в строке состояния).

Число оставшихся окон — главная проверка сценария: четыре открылось, два
закрылось. Другое число значит меню, которое не раскрылось, щелчок, который
не туда попал, или закрытие, которое не закрыло, — и по картинке не понять,
что именно.

## Устройство

| Файл | Что в нём | Чистый C |
|---|---|---|
| `desktop.c` | цикл событий, мебель стола, его меню | нет |
| `dsk_rect.c` | прямоугольники и список повреждений | да |
| `dsk_layout.c` | раскладка от размера экрана | да |
| `dsk_paint.c` | рисовальщик: надстройки над шестью операциями | да |
| `dsk_paint_surface.c` | те шесть операций поверх системной поверхности | нет |
| `dsk_wm.c` | окна: геометрия, z-порядок, попадание, перетаскивание | да |
| `dsk_menu.c` | строка меню и раскрывающиеся меню | да |
| `dsk_dlg.c` | модальные диалоги | да |
| `dsk_cursor.c` | программный указатель | нет |
| `dsk_icons.c` | значки 16×16, картинками | нет |
| `dsk_folder.c` | окно папки: чтение, список, прокрутка | нет |
| `dsk_run.c` | отдать машину программе и забрать обратно | нет |

«Чистый C» — без `argon.h`, то есть **собирается и проверяется на ПК**.
Юнит-тесты — `host-tests/test_desktop.c`, идут в `argon tests`; они
подставляют вместо экрана рисовальщик-регистратор и проверяют то, что на
панели не видно: геометрию рамки, во что попадает точка, какие окна
перерисовывает данное повреждение и **в каком порядке**, и что ни одна
заливка не вышла за выданный клип.

**Всё рисование идёт через таблицу из шести функций** (`dsk_painter_t`), и это
решение с причиной: единственная плата с тачем (CYD) не может держать
поверхность 320×240 вообще, и показать на ней этот стол сможет только
растеризатор полосами через `gfx->present`. Второй бэкенд посилен, пока у него
шесть функций, и невозможен, когда оболочка зовёт `ag_gfx_*` из сорока мест.
Побочная выгода уже получена: та же таблица позволила проверить оконный
менеджер тестами.

## Правило программного указателя

Пока указатель на экране, под ним ничего рисовать нельзя: сохранённые
пиксели станут устаревшими, и возврат затрёт нарисованное. Поэтому любая
перерисовка — **спрятать, нарисовать, показать**, в этом порядке, всегда.

## Запуск: экран отдаётся, ввод нет

Модель Program Manager: оболочка отпускает дисплей, программа владеет всем
экраном, по выходе стол возвращается. Первая половина работает —
`GFXDEMO.AXE`, запущенный из «Выполнить…», рисует свою картинку на весь
экран, то есть передача дисплея и загрузка образа в порядке.

Вторая половина нет. Измерено:

- консольная `HELLO.AXE` загружается, завершается с кодом 0 и **не печатает
  ничего** — её вывод не доходит до транскрипта;
- `GFXDEMO.AXE` не видит ни `q`, ни `Esc`: она остаётся на экране, и стол не
  возвращается;
- ожидание «нажмите клавишу» после консольной программы срабатывает
  мгновенно, то есть в очереди уже лежало что-то не то.

Три симптома — одна причина: **ребёнок приложения не получает того
маршрутизирования консоли и ввода, которое получает ребёнок шелла.** Сессия
считает передним планом саму оболочку. Попытка отдать передний план явно
(`spawn` вместо `exec`, потом `proc->foreground(pid)`, потом `wait`) картину
не изменила — так что дело не в этом флаге, а в том, как сессия связывает
слот с процессом.

Это вопрос ядра и сессий, не стола, и он требует отдельного разбора: пока он
не закрыт, стол может запустить программу, но не может вернуть себе экран
иначе как её собственным выходом.

## Правило обводки

Окно тянется контуром в один пиксель, а не телом. Это не стилизация: по
проводу к CYD движущаяся картинка стоит 3.5 кадра в секунду, и тащить окно
телом — значит это увидеть.

Под контуром сохраняются пиксели, как под указателем, и отсюда два правила,
каждое из которых уже было нарушено и измерено:

1. **Один `flush` на всю обводку, а не четыре полоски.** Панели отдаются
   целые строки, поэтому левая и правая полоски стоят каждая столько строк,
   сколько занимает окно. Восемь отправок кадра на одно движение мыши — и
   указатель отстаёт на секунды, очередь событий копится, отпускание кнопки
   приходит позже, чем перемещения, и окно уезжает не туда.
2. **Перед перерисовкой обводку надо снять, после — вернуть.** Иначе её
   копия подложки устаревает, и следующее движение возвращает на экран
   картинку, которой там уже нет: чёрный прямоугольник, приколоченный к
   столу, который не убирает даже принудительная перерисовка (F5) — потому
   что именно перерисовка его и портит.

Обе ошибки видны на снимке как одно и то же, и обе сначала были приняты за
третье. Числа: 3267 различающихся пикселей после F5 против 37 теперь.

## Правило фокуса

**Нельзя рисовать, пока слот не получил фокус.** Процесс попадает в слот
сессии не сразу — здесь измерено 90 мс после первой инструкции, — и до этого
`gfx_may_present` в ядре отбрасывает каждый `flush`. При этом `acquire`
отвечает «да», рисующие вызовы молчат, и на стекле остаётся консоль.

Оболочка поэтому ждёт фокуса (не дольше двух секунд, иначе машина без слоёв
сессий была бы машиной, где она висит) и печатает в транскрипт `focus yes`.
На `AG_EV_FOCUS_GAINED` — полная перерисовка, на `AG_EV_FOCUS_LOST` —
перестать рисовать.

Ядро тоже исправлено: владелец дисплея теперь может отправлять кадр, не
дожидаясь фокуса. Сессия отбирает дисплей, когда фокус уходит, так что
владелец по построению и есть тот, кому положено рисовать.

Как это выглядело, пока не было исправлено: первый кадр приходил половиной.
И зависело от размера — на 320×240 оболочка проигрывала гонку **всегда**, на
640×400 выигрывала, потому что вчетверо больше пикселей заливаются дольше,
чем сессия успевает выдать фокус.

## Что нашлось по дороге (и почему стенд работает только теперь)

Шесть починок вне этой папки, все — причины, а не симптомы:

1. **`components/argon_port/idf/src/panel_hw.c` не подключал `sdkconfig.h`,**
   а проверял `#if CONFIG_ARGON_PANEL_QEMU`. Неопределённый макрос в `#if` —
   это ноль, так что вся RGB-панель QEMU вырезалась препроцессором молча.
   Окно SDL при этом открывалось — своего размера 800×600 — и оставалось
   чёрным. Единственный видимый признак: окно не того размера, которого
   просил гость.
2. **QEMU не создаёт RGB-панель без `-M esp32s3,graphics=on`.** Это опция
   машины, а не устройство; `-device esp_rgb` не существует.
3. **KBDVIRT выбрасывал байты со свежепринятого сокета** (`drain_rx` в
   `try_accept`). Клиент, который подключается и сразу печатает, успевает
   прислать клавишу до того, как гость примет соединение на своём такте в
   10 мс. Клавиша доходила в одном прогоне из трёх.
4. **`ensure_listen` в обоих виртуальных драйверах затирал хороший
   дескриптор.** Его зовут два потока (такт ввода ядра и шелл), оба видят
   `listen < 0` до того, как кто-то сохранит результат, проигравший получает
   `-AG_EBUSY` и пишет `-1` поверх сокета победителя. Порт после этого закрыт
   до конца загрузки, а лог за миллисекунду до этого сообщает, что порт
   открыт. Это и была вся нестабильность стенда.
5. **`gfx_may_present` проверял фокус вместо владения** — см. «Правило
   фокуса» выше. Владелец дисплея теперь может отправлять кадр.
6. **`mksysfs.py` не умел собрать образ без пакета платы**, а `--display`
   задавал только имя драйвера, не размер. Теперь есть `--board none` и
   `--display-size WxH`; плюс `[display]` дописывается после `--add`, а не
   до, иначе `--add свой.cfg=SYSTEM.CFG` молча выбрасывал override.

Плюс три умения стенда: `qemu-boot.ps1 -Gfx` (окно панели), элементы
`-Send` с префиксом `!` (команда на хосте посреди сценария — иначе нечем
пошевелить мышью, пока приложение работает и приглашения нет) и
`-SysFs <образ>` (готовый раздел C:, вложенный в образ прошивки).

`tools/inputplay.py` перенесён сюда из ветки `worktree-fallout-cxx`: в `main`
его не было.

## Ловушка, из-за которой стенд выглядел мёртвым

Виртуальные драйверы не начинают слушать, пока что-нибудь не откроет
устройство или не придёт такт ядра. Поэтому `inputplay` подключается только
после того, как оболочка уже запущена; раньше — отказ в соединении и плата,
которая кажется мёртвой.
